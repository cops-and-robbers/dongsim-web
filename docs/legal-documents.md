# 법적 문서 시스템 (개발자용)

이용약관·개인정보 처리방침·위치정보 이용약관·마케팅 수신 동의 4종을 사이트와 앱이 함께 쓰는 구조.

## 왜 이렇게 됐나

같은 문서가 두 곳에 있었다. 앱은 `assets/legals/*.json` 을 빌드에 넣어 Flutter 위젯으로 그렸고, 웹은 `lib/policies/*.json` 을 읽어 사이트 디자인으로 그렸다. 2026-08-24 기준 두 벌의 내용은 완전히 같았지만, **맞춰주는 장치가 없고 사람이 손으로 동기화하는 구조**였다. 한쪽만 고치면 조용히 어긋나고, 그게 법적 문서다.

거기에 일본 출시 이후 문제가 하나 더 생겼다. JSON 이 한국어뿐이라 일본 사용자도 한국어 약관을 본다. 앱에 언어별 JSON 을 넣으면 4종 × 3언어 = 12개가 되고, 문구 하나 고칠 때마다 12개를 손봐야 한다. 하드코딩 한국어는 iOS 심사 리젝 전례도 있다(FE #446).

그래서 **웹을 정본으로 삼고 앱이 웹뷰로 가져가는** 방향으로 정했다(#47). 문서를 고칠 때 앱 심사를 다시 받지 않아도 되고, 언어를 늘릴 때 앱을 안 건드려도 된다.

## 데이터 흐름

```
content/legal/<locale>/<doc>.json     ← 정본. 여기만 고친다
  │
  ├─ lib/legal/documents.ts           ← 슬러그 매핑 + 타입
  │    │
  │    ├─ components/policy/PolicyRenderer.tsx  → /terms /privacy /location /marketing
  │    │     사이트 디자인. 다크 모드·반응형. 사람이 브라우저로 읽는 화면
  │    │
  │    └─ lib/legal/embed-html.ts               → /legal/[doc]/embed
  │         + lib/legal/embed-route.ts            → /ja/… /en/…
  │          앱 화면 재현. 앱 웹뷰가 여는 화면
  │
  └─ scripts/build-legal-fonts.py     → public/fonts/legal/*.woff2
                                      + lib/legal/font-manifest.json
```

문서는 하나인데 그리는 방식이 둘이다. 한 컴포넌트에 분기를 넣지 않고 나눈 것은, 한쪽을 고칠 때 다른 쪽이 깨지지 않게 하려는 것이다. 사이트 화면은 사이트 규칙을 따르고 앱 화면은 앱 규칙을 따르는데, 그 둘이 반대 방향이라 한 곳에 두면 계속 부딪힌다.

## 경로가 둘인 이유

| 경로 | 누가 여나 | 껍데기 |
| --- | --- | --- |
| `/terms` `/privacy` `/location` `/marketing` | 사람·검색엔진·스토어 심사 | 사이트 헤더·푸터 |
| `/legal/<doc>/embed` | 앱 웹뷰 | 없음 |

앞의 넷은 **절대 바꾸거나 없애면 안 된다.** 스토어 심사 정보와 검색 색인이 그 주소를 쓰고 있다.

뒤의 경로는 `robots.ts` 와 `X-Robots-Tag` 양쪽에서 색인을 막는다. 같은 내용이 두 주소로 잡히면 중복 취급을 받는다.

## embed 는 왜 Route Handler 인가

`app/layout.tsx` 는 모든 라우트를 감싸고 Header·Footer·GTM 을 넣는다. `page.tsx` 로 만들면 이걸 벗어날 수 없다. 실측하면 이렇게 된다.

| | page.tsx | route.ts |
| --- | --- | --- |
| HTML | 111 KB | **27 KB** |
| JS 청크 | 7개 | **0개** |
| GTM | 실림 | **없음** |
| 헤더·푸터·JSON-LD | 실림 | **없음** |

GTM 이 앱 안까지 따라오면 **앱에서 약관을 열 때마다 웹 페이지뷰가 GA4 에 찍힌다.** 어드민 트래픽까지 걸러낸 마당에 앱 웹뷰가 웹 통계로 섞이면 안 된다.

Route Handler 는 레이아웃을 타지 않으므로 응답을 통째로 우리가 정한다. 그리고 앱이 이 HTML 을 기기에 저장해 `file://` 로 열 계획이라(아래 3단계), 외부 참조가 적을수록 좋다. CSS 는 인라인이고 밖에 있는 건 폰트뿐이다.

## 앱 화면을 어떻게 재현했나

원본은 FE `lib/core/widgets/pages/legal_document_page.dart` 다.

```
본문 padding 16
├ [비-ko 로케일만] 고지 배너  #EDF0F2 · radius 12 · padding 16
├ 섹션들 (사이 24)
│    heading   SemiBold 14 · #080A0C
│    ↓ 8
│    content   Medium 12 · #333D48 · line-height 1.4
│    ↓ 8
│    items[]   각 위 4
│      └ subItems[]  좌 16 들여쓰기 · 각 위 2
└ 하단 여백 64
```

색은 앱 `AppColors` 그대로 넷이다. `white #FFFFFF` · `black #080A0C` · `black800 #333D48` · `black100 #EDF0F2`.

### 스케일 - `--u`

앱은 `flutter_screenutil` 을 쓰고 디자인 기준이 `Size(393, 852)` 다. **`12.sp` 는 12px 이 아니라 기기 폭에 비례한다.** CSS 에 `font-size: 12px` 를 그대로 쓰면 큰 폰에서 앱보다 작아 보인다.

```css
:root { --u: clamp(0.9px, calc(100vw / 393), 1.2px); }
h2   { font-size: calc(14 * var(--u)); }
```

`--u` 는 "앱 논리픽셀 1개"다. 앱 값을 그대로 곱해 쓰면 된다. `:root` 의 `font-size` 를 건드리지 않은 것은 그러면 사이트 전체가 흔들리기 때문이고, `em` 을 쓰지 않은 것은 중첩되면 값이 곱해져 계산이 어려워지기 때문이다.

상·하한은 태블릿이나 데스크톱 브라우저로 열렸을 때를 위한 것이다. 393px 뷰포트에서는 `--u` 가 정확히 1px 이 되어 모든 값이 앱과 일치한다(실측 확인).

**`letter-spacing` 만 `px` 고정이다.** 앱에서도 `.sp` 가 안 붙어 있어 기기 크기와 무관한 절대값이다.

### 다크 모드를 두지 않는다

`AGENTS.md` 의 테마 색 쌍 규칙을 embed 에서는 따르지 않는다. 앱의 `LegalDocumentPage` 가 라이트 고정이라, 여기서만 어두워지면 앱 화면과 이질감이 생긴다. **이건 규칙 위반이 아니라 의도된 예외다.**

### 사이트 렌더러와 일부러 다르게 한 것

| | `PolicyRenderer` (사이트) | `embed-html` (앱) |
| --- | --- | --- |
| 제목·시행일 헤더 | 따로 그림 | **안 그림** |
| 첫 섹션 | 제목 중복이라 걸러냄 | **그대로 그림** |
| 본문 문단 | `\n\n` 으로 잘라 `<p>` 여러 개 | **자르지 않고 `pre-line`** |
| subItem 기호 | `-` 를 붙임 | **안 붙임** |

앱은 AppBar 에 제목을 그리고 본문 첫 섹션이 이미 제목과 시행일을 담고 있다. 여기서 또 그리면 두 번 나온다. 본문을 자르지 않는 것은 앱이 `content` 문자열 하나를 `Text` 위젯 하나로 그리기 때문이고, 자르면 문단 간격이 붙어 높이가 어긋난다.

## 폰트 서브셋

embed 는 레이아웃을 타지 않아 `next/font` 가 넣어주는 Pretendard 를 못 쓴다. 직접 서빙해야 하는데 원본이 웨이트당 760KB 다. 약관 한 장을 띄우려고 1.5MB 를 받게 할 수는 없다.

문서에 실제로 쓰이는 글자만 남기면 **웨이트당 52KB** 가 된다.

```bash
python scripts/build-legal-fonts.py   # 필요: pip install fonttools brotli
```

문서를 고쳐 새 글자가 생기면 다시 돌려야 한다. 안 돌리면 그 글자만 시스템 폰트로 떨어져 한 문단 안에 서체가 섞인다. **화면을 안 열어보면 모르는 종류의 사고**라 검사를 붙여 두었다.

```bash
pnpm check:legal-fonts
```

글자 집합 해시를 `lib/legal/font-manifest.json` 과 비교한다. 폰트 파일을 파싱하지 않으므로 CI 에 파이썬이 없어도 돈다. `build-legal-fonts.py` 의 `ALWAYS` 와 `check-legal-fonts.mjs` 의 `ALWAYS` 는 **같아야 한다.** 한쪽만 고치면 해시가 어긋나 검사가 항상 실패한다.

## 오픈소스 라이선스 문서

문서 4종과 같은 구조를 쓰지만 성격이 다르다. 사람이 쓴 글이 아니라 `pubspec.lock` 과 서버 의존성에서 뽑아낸 목록이다(#51).

세 구역으로 나뉜다.

```
지도 및 주소 데이터    OpenStreetMap · Geoapify   ← 표기 의무가 있는 부분
앱                    패키지 218개, 라이선스 본문 28종
서버                  패키지 22개, 라이선스 이름만
```

지도 데이터 표기가 이 문서를 만든 이유다. 커뮤니티 모집글의 주소는 Geoapify 역지오코딩 결과이고, Geoapify 는 OpenStreetMap 기반이라 표기가 필요하다. 무료 플랜이라 Geoapify 표기도 함께 한다.

### 왜 같은 라이선스 이름이 여러 번 나오나

라이선스 본문이 완전히 같은 것끼리만 묶었다. MIT 를 쓰는 패키지라도 저작권자마다 문구가 조금씩 달라서, 그대로 싣다 보면 `MIT License` 섹션이 네 번 나온다. 문서 앞머리에 그 이유를 적어 두었다.

이름만 보고 묶으면 실제와 다른 문구를 싣게 되므로 그렇게 하지 않는다.

### 서버 패키지는 이름만 싣는다

서버 소프트웨어는 이용자에게 배포되지 않아 고지 의무가 없다. 무엇을 쓰는지 밝히는 것이 목적이라 패키지명과 라이선스 이름까지만 둔다.

### 목록 갱신

지금은 손으로 만든 목록을 커밋해 두었다. 의존성이 바뀌었는데 목록을 안 고치면 아무도 모르는 종류의 문제라, 앱 쪽에 패키지 집합 변경을 잡는 검사를 붙이는 것이 FE 후속 작업으로 남아 있다. 폰트 서브셋 검사와 같은 방식이다.

### 파일 이름에 해시가 붙는 이유

`public/` 에 직접 넣은 파일은 Vercel 이 `max-age=0, must-revalidate` 로 내보낸다. 그래서 약관 화면 한 번에 왕복이 세 번 생긴다 - HTML 한 번, 폰트 두 번. 본문은 전부 304 라 데이터는 안 쓰지만 왕복 자체는 매번 발생하고, 느린 망에서는 시스템 폰트로 먼저 그려졌다가 Pretendard 로 튀는 게 보인다.

그래서 파일 이름에 woff2 내용의 sha256 앞 8자리를 넣는다(#49).

```
pretendard-500.f79e2ecd.woff2
```

이름이 같으면 내용도 같다는 게 보장되므로 `next.config.ts` 가 `/fonts/legal/` 전체에 `immutable` 을 건다. 폰트를 다시 만들면 이름이 바뀌고, 그 이름을 적어둔 HTML 은 어차피 매번 재검증되니 앱은 곧바로 새 이름을 알게 된다.

**글자 집합 해시를 파일 이름에 쓰면 안 된다.** Pretendard 원본 버전이 올라가면 글자 집합은 그대로인데 woff2 내용은 바뀐다. 그때 이름이 안 바뀌면 낡은 폰트가 1년간 박제된다. 출력된 바이트를 해싱해야 한다.

`public/fonts/legal/` 에 이름이 고정인 파일을 두면 안 되는 것도 같은 이유다. 매니페스트를 `lib/legal/` 에 둔 것은 그래서다.

## 언어 늘리기

`content/legal/ja/` 를 만들고 그 안에 같은 이름의 JSON 넷을 두면 된다. 그다음 `lib/legal/documents.ts` 의 `KO` 상수를 `Record<Locale, ...>` 로 한 겹 늘린다. 지금 한 겹인 것은 ko 뿐이라서다.

폴더를 미리 언어별로 나눠 둔 것은, 한국어 하나뿐인 지금은 과해 보여도 **일본어를 넣는 순간 파일명이 지저분해지고 앱이 로케일로 URL 을 만들 때 규칙이 안 서기** 때문이다.

번역본에는 원문이 한국어라는 고지가 필요하다. `renderLegalEmbedHtml` 의 `notice` 인자가 그 자리다. 앱은 이미 `legalDocumentKoreanOnlyNotice` 로 같은 배너를 갖고 있다.

## 앱 쪽 진행 단계

| 단계 | 하는 일 | 상태 |
| --- | --- | --- |
| 1 | 웹에 embed 뷰 만들기 | **이 문서** |
| 2 | 앱이 원격 URL 을 웹뷰로 열고 `assets/legals/` 삭제 | FE 이슈 |
| 3 | 앱이 HTML 을 받아 저장하고 `file://` 로 열기 (파일 캐시) | FE 이슈 |
| 4 | `ja` · `en` 추가 | 양쪽 |

2단계에서 앱의 JSON 을 지우는 순간이 **중복이 실제로 사라지는 시점**이다. 그전까지는 여전히 두 벌이다.

3단계의 갱신 판정은 HTTP `ETag` 로 한다. Vercel 이 이미 붙여주고 조건부 요청에 304 를 반환하는 것을 확인했으므로 서버 추가 작업은 없다. 문서가 안 바뀌었으면 헤더만 오가고 본문은 안 받는다.

## 보류된 것 (다시 제안하기 전에 확인)

- **동의 이력 버전 컬럼**: 백엔드는 `terms_agreed_at` 만 저장하고 버전은 없다. 다만 과거 버전이 URL 로 보존되면 날짜만으로 역추적된다. 버전 필드가 진짜 필요해지는 것은 **재동의 판정**을 만들 때이고, 그건 별도 이슈다. ETag 는 바이트가 1개만 달라도 바뀌므로 재동의 판정에는 못 쓴다
- **매니페스트 API**: 문서 4종 × 언어 3개라도 앱은 **현재 로케일 4개**만 받으면 된다. 조건부 요청 4번이면 충분하고 대부분 304 다. 요청을 1번으로 줄이는 이득보다 API 를 안 만드는 단순함이 크다
- **엣지 캐시**: 응답에 `Age: 551044`(약 6일)가 찍힌 적이 있다. 배포 시 무효화되지만, **문서를 고치고 배포한 뒤 앱에 반영되기까지 걸리는 시간은 한 번 실측해야 한다**

## 언어

`content/legal/` 아래를 언어별 폴더로 나눈다. `ko` 가 원본이고 `ja`·`en` 은 번역이다.

라우트도 언어별로 있다. 사이트용은 `/terms` `/ja/terms` `/en/terms`, 앱 웹뷰용은
`/legal/terms/embed` `/ja/legal/terms/embed` `/en/legal/terms/embed` 다.
Route Handler 는 파일 경로가 곧 라우트라 로케일을 인자로 못 받는다. 그래서 로케일마다
파일을 두되 본문은 `lib/legal/embed-route.ts` 한 곳에 모아 세 라우트가 갈라지지 않게 했다.

### 번역본에만 있는 섹션

각 번역본에는 원본에 없는 섹션이 하나씩 더 있다.

```
ja   日本国内の利用者に関する特則
en   Provisions for Users Outside the Republic of Korea
```

일본 소비자계약법, 일본 민법상 미성년자 기준(18세), 국제재판관할, APPI 대응처럼
**번역으로는 만들 수 없는 내용**이다. 원문에 대응 조항이 없으니 번역이 아니라 신설이다.

그래서 각 문서 부칙의 "원문 우선" 원칙에 예외를 달아뒀다. 예외를 달지 않으면
일본법 대응하려고 넣은 조항이 "한국어가 우선"이라는 문장 때문에 참고사항으로 격하된다.

개인정보 처리방침에는 안전관리조치에 「외적 환경의 파악」 항목도 추가돼 있다.
일본 개인정보보호위원회가 외국에서 개인데이터를 취급할 때 그 나라 제도를 파악하고
공표하도록 요구하는 항목이라, 처리 국가(한국·미국)를 함께 적는다.

**번역본을 고칠 때는 이 섹션들이 원본과 대응하지 않는다는 걸 전제로 봐야 한다.**
`ko` 와 항목 수가 다른 것은 오류가 아니다.

## 한국어 원문에 남아 있는 것

번역 과정에서 원문의 문제 몇 개를 발견했지만 **고치지 않았다.**

- 이용약관 제10조 ⑤, 제19조 ① - 무료 서비스에 대한 면책 범위
- 위치정보 약관 제14조 ①② - 책임 기준이 서로 다르다
- 위치정보 약관 제15조 ②~④ - 고의·과실 단서가 빠져 있다
- 위치정보 약관 제17조 - "상호 및 주소 등" 이라 해놓고 주소가 없다

약관 내용 수정은 **앱 `assets/legals` 와 Google Sites 까지 동시에 고쳐야 하고**,
제3조에 따라 시행 7일 전(불리한 변경은 30일 전) 사전 공지가 필요하다.
파일만 고친다고 효력이 생기지 않는다. 별도 이슈에서 법무 검수 결과와 함께 다룬다.
