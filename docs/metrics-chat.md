# 지표 챗봇 (#163)

어드민 지표 화면의 "물어보기" 창. 팀원이 지표를 말로 물으면 숫자를 찾아 답한다.
코드는 `lib/metrics/chat/`, 라우트는 `app/api/admin/metrics/chat/route.ts`, 화면은 `components/admin/metrics/AskPanel.tsx`.

## 화면: 탭도 옆 패널도 아니라 떠 있는 창

처음엔 지표 화면의 여섯째 탭이었다. 질문은 그래프를 보다 생기는데("이날 왜 튀었지?"), 탭이면 그래프를 떠나야 물을 수 있고 답의 숫자를 그래프에서 다시 찾으려면 탭을 오가야 했다. 그래서 어느 탭에서든 여는 옆 패널로 옮겼는데, 화면 한쪽을 통째로 덮는 느낌이라는 말을 듣고 오른쪽 아래에 떠 있는 작은 창(380px)으로 다시 바꿨다(2026-10-10). 채팅 상담 창처럼 익숙한 자리이고 지표 화면 배치는 건드리지 않는다.

- 여는 곳: 머리말의 "물어보기" 버튼, 또는 치즈를 짧게 누르기. 주소에 `?ask=1` 로 남는다(예전 `?tab=ask` 도 창으로 연다)
- 휴대폰은 아래에서 올라오는 시트. 치즈는 시트 윗변에 올라선다
- 답의 "지표 화면에서 이 기간 보기"를 누르면 창을 접어 그래프가 다 보이게 하고, 치즈가 "이 기간을 열었어요"라고 알린다
- 말풍선은 알림 한 줄만(`petSay`). 창을 접어 둔 사이 답이 오면 "답 찾았어요", 처음 온 사람에게 한 번 "누르면 물어볼 수 있어요"(창이 닫혀 있을 때만). 누르면 창이 열린다. 답 자체를 말풍선에 넣지 않는 건 숫자 비교와 막대가 들어가야 해서다
- 치즈는 창을 가리지 않고 그 왼쪽에 선다. 창이 덮으면 달려 나온다
- 질문할 때 화면에 걸린 탭과 기간(`view`)을 같이 보낸다. 서버가 `parseView` 로 모양을 확인한 뒤 지시문의 "화면에서 보고 있는 것"에 넣어, 기간이 없는 질문과 "이 기간"을 그 날짜로 푼다
- 추천 질문은 지금 탭에 맞춘 둘(`TAB_SUGGESTIONS`)을 앞에 두고, 서버가 만든 질문(크게 움직인 지표, 최근 행사, 고정 질문)을 더해 넷까지
- 닫아도 대화는 남는다. 서버 상태(남은 질문 수, 추천)는 처음 열 때 한 번만 받는다

### 답의 모양: AI 티를 걷어 낸 것

패널의 첫 모양은 "인공지능이 만든 화면" 같다는 말을 들었다(2026-10-10). 섹션 제목을 단 카드 네 겹("데이터로 확인한 것", "가능한 이유", "읽을 때 조심할 것", "어떻게 계산했나요"), 알약 모양 추천 질문, "이 답이 도움이 됐나요?" 문장, 설명 단락이 겹쳐 있었다. 분석 도구의 챗봇을 다시 보고 바꿨다.

| 바꾼 것 | 참고한 곳 |
| --- | --- |
| 답은 숫자가 먼저. 도구 결과를 지표 화면과 같은 모양(비교는 "30 → 42건 ↑40%", 날짜별은 작은 선, 나눠 보기는 막대)으로 그린다(`evidence.ts`, `AskAnswer.tsx`). 모델이 쓴 글이 아니라 도구 결과 그대로라 화면과 바로 대조된다 | Mixpanel Spark(답이 곧 보고서), Amplitude(답 안의 차트 미리보기) |
| 근거마다 "지표 화면에서 이 기간 보기". 같은 기간, 같은 탭, 다른 비교 기간이면 직접 고른 비교까지 연다 | Metabase Metabot, Spark 의 "편집기로 열기" |
| 지금 보는 탭과 기간을 입력창 위에 적는다. 무엇을 기준으로 답할지 묻기 전에 보인다 | PostHog AI 의 현재 페이지 맥락 |
| 비서는 치즈. 찾는 동안 킁킁, 확인 못 한 답엔 갸웃, 오류엔 시무룩, 연결 전엔 졸고 있다. 반짝이 아이콘은 쓰지 않는다 | PostHog 의 고슴도치 |
| 답 글은 말풍선, 카드 없이 치즈 얼굴 옆에. 첫 문장이 답이고 사실은 같은 단락으로 잇는다 | |
| 확인 못 한 문장은 물결 밑줄과 한 줄 안내. 큰 경고 딱지 대신 | 문장 단위 인용(claim-level citation) |
| 추측은 "확인하지 않은 추측 N개"로 접어 둔다. 확인한 것과 같은 무게로 보이지 않게 | |
| 추천, 후속 질문은 알약 대신 줄 목록. 평가는 문장 대신 엄지 아이콘 둘. 남은 질문 수는 다섯 개 아래로 남았을 때만 | |

근거 그림은 답의 사실이 인용한 도구 호출만, 답에 나온 숫자가 든 지표만 고른다(지표 22개를 다 늘어놓지 않는다). 서버 안내문도 그 지표와 상관있는 것만 붙이고 날짜는 "10월 5일"로 바꾼다. 시험은 `evidence.test.mjs`.

## 구조와 이유

숫자를 지어내지 않는 것이 이 기능의 전부다. 그래서 모델에게 맡기는 일을 줄였다.

| 단계 | 누가 | 왜 |
| --- | --- | --- |
| "지난주" 같은 말을 날짜로 | 서버(`periods.ts`) | 모델이 날짜를 세다 틀린다 |
| 데이터 읽기 | 도구 7개(`tools.ts`)만. SQL 은 쓰지 않는다 | 정해 둔 집계(지표 화면과 같은 `loadDashboard`)만 읽으면 화면과 숫자가 같다. 못 하는 질문은 못 한다고 실패한다 |
| 차이, 증감률, 행사 전후 | 도구가 계산해서 준다 | 모델의 산수는 자신 있게 틀린다 |
| 답 | 모델. 사실(인용 필수), 가설, 주의점, 후속 질문으로 나눠서 | 확인한 것과 추측을 화면에서 다르게 보여 준다 |
| 검증 | 코드(`verify.ts`) | 사실의 숫자가 인용한 도구 결과에 있는지, 사실에 원인 단정("때문에", "덕분에")이 없는지 본다 |
| 걸리면 | 걸린 곳을 알려 주고 한 번만 다시 쓰게. 그래도 걸리면 "숫자를 확인하지 못했어요" 표시 | 숨기지 않는다 |

조사 근거(2026-10-09): 지표 정의를 고정한 도구 방식이 SQL 생성보다 정확하고, 틀릴 때 "못 한다"고 실패했다(dbt 실험). LLM 은 상관에서 인과를 거의 찍듯이 고른다(Corr2Cause). 계산을 코드로 넘기면 정확도가 오른다(Program of Thoughts).

### 전체 기간과 "왜": 지표를 통째로 보내지 않는 이유

"전체 기준으로도 묻고 싶다", "DB 에 있는 걸 다 보내 인과까지 보게 하면 어떨까"를 검토했다(2026-10-10). 날짜별 지표를 통째로 보내지 않고 이렇게 했다.

- 통째로 보내면 숫자가 틀린다. 6개월치 날짜별 지표 20여 개면 숫자가 4천 개쯤인데, 모델이 직접 더하고 나누면 그럴듯하게 틀리고 그 합은 도구 결과에 없어 검증이 무너진다
- 많이 줄수록 우연히 같이 움직인 것을 원인으로 짚는다(Corr2Cause). 날짜별 합계 같은 관찰 데이터로는 인과를 증명할 수 없다
- 질문마다 수만 토큰이라 무료 키의 분당 한도에 걸리고, 무료 등급은 보낸 내용이 학습에 쓰인다

대신 한 것

| 무엇 | 어디 |
| --- | --- |
| "전체(수집 시작부터, 지금까지, 누적)", "최근 13주"를 기간 표에 넣었다. "전체"는 화면에 걸린 기간이 아니라 이 행으로 푼다 | `periods.ts`, `instructions.ts` |
| 한 번에 볼 수 있는 기간을 366일에서 731일로 | `tools.ts` MAX_DAYS |
| 훑어보기 도구 `metrics_overview`: 지표마다 주(30주 넘으면 달) 합계, 전체 합계, 바로 앞 칸보다 50% 넘게 움직인 칸(movers, 둘 다 20 이상, 온전한 칸끼리), 같은 기간 일정과 칸별 게시물 수. 묶음과 변화율은 코드가 계산하고 모델은 고르고 설명만 한다 | `tools.ts` |
| "왜"는 순서를 정했다: 무엇이 언제 움직였나(movers, 날짜별) → 같은 시기 일정, 받은 길, 유입 경로, 행사 전후 비교 → 그 결과로 가설 | `instructions.ts` |
| 가설도 인용한다. 확인하려고 돌린 비교가 있으면 그 결과의 숫자로 쓰고 toolCallId 를 단다. 검증기는 인용한 결과에 그 숫자가 있는지 본다. 화면은 "비교해 봄"과 "확인 못 함"을 나누고, 비교해 본 가설엔 그 비교 그림을 붙인다 | `run.ts`, `verify.ts`, `AskAnswer.tsx` |

2026-10-10 실데이터 확인(가짜 모델, 읽기만): 전체(4월 1일~어제) 훑어보기가 28주, 약 2.2초, 결과 약 14KB. 21개 지표의 훑어보기 합계가 같은 기간 합계 도구와 모두 같았다. "지금까지 설치 추세", "지난주 어땠어" 둘 다 다시 쓰기 없이 검증을 통과했다.

### 지표 점검: 무엇을 더했고 무엇이 아직 없나

챗봇이 "행사 → 설치 → 가입 → 실제 게임"과 "왜"에 답하려면 필요한 숫자를 다시 봤다(2026-10-10).

이미 모아 지표 화면에 보이는데 챗봇만 못 보던 것을 `catalog.ts` 에 더했다.

| 지표 | 왜 필요한가 |
| --- | --- |
| site_conversion 사이트 전환율, download_link_clicks QR과 링크트리 이동 | 사이트를 고쳤을 때, 행사 QR 이 얼마나 쓰였나 |
| appstore_from_search, appstore_from_link App Store 받은 길(날짜별) | 행사 주에 링크로 받은 사람이 늘었나. 원인 가설을 확인하는 가장 직접적인 숫자 |
| activation_rate, d1_return, d7_return 활성화율과 재방문 | 설치가 늘어도 게임까지 가는지, 다시 오는지 |
| android_removes, android_remove_rate, play_uninstalls 삭제 | 설치가 늘 때 삭제도 같이 늘었나 |
| game_starts_app 게임 참가(앱 기록) | 게임 서버를 못 읽을 때 대신 |

게임 서버 기록으로 새로 센 것(`server.ts`). 마케팅의 끝을 직접 본다.

| 지표 | 세는 법 |
| --- | --- |
| new_players 첫 게임을 한 새 가입자 | 가입이 2026-08-17(참가자 기록 시작) 이후인 사람의 첫 판 날. 그 전 가입자는 첫 판을 알 수 없어 뺀다 |
| signup_activation 가입 후 7일 안 첫 게임 비율 | 기간 안 가입자 중 7일 안에 한 판이라도 한 비율. 7일이 다 지난 가입자만 분모에 |

비율 지표는 분자와 분모를 같이 돌려주고, 두 기간 차이는 %p 로만 낸다(23% 에서 25% 를 "8.7% 늘었다"고 하지 않는다).

아직 데이터가 없어 답할 수 없는 것. 챗봇은 이런 질문에 "볼 수 없다"고 답한다.

| 질문 | 필요한 것 |
| --- | --- |
| 행사에 몇 명이 왔고, 그중 몇 명이 설치했나 | 일정(이벤트 달력)에 현장 참가 인원, QR 스캔 수를 적는 칸. 지금은 날짜와 이름만 있다 |
| Android 설치가 어느 경로(행사 QR, 인스타, 검색)에서 왔나 | 다운로드 링크 꼬리표(#144) 배포 뒤 Play 설치 리퍼러 |
| iOS 설치가 어느 캠페인에서 왔나 | App Store 캠페인 리포트 수집 |
| 인스타 게시물 하나가 설치까지 이어졌나 | 게시물별 링크 꼬리표(UTM)와 설치 경로가 이어져야 한다. 지금은 게시물별 링크 클릭까지만 |
| 광고나 홍보에 쓴 돈 대비 효과 | 캠페인별 비용 기록. 지금은 없다 |
| 새 가입자 첫 게임 비율(8월 17일 전) | 참가자 기록이 그 전에는 없어 볼 수 없다 |

게임 서버 숫자(가입, 판 수, 참가 인원, 새 가입자 첫 판)는 요청한 어드민의 토큰으로 읽고, 날짜별 합계만 모델에 준다. 닉네임과 사용자 id 는 모델에 가지 않는다(가입일과 첫 판 날만 서버 안에서 맞춰 본다).
관리자만 참가한 판은 시험 판으로 보고 뺀다. 참가자 기록이 있는 2026-08-17 이후만 가릴 수 있다(`server.ts`).

## 처음 켜기: 두 길

| | A. AI Studio 무료 키 | B. Vertex AI + Pro 크레딧 |
| --- | --- | --- |
| 돈 | 결제 등록이 없어 나갈 수 없다 | 월 10달러 크레딧 안, Spend Cap |
| 보낸 내용 | 구글이 서비스 개선에 쓰고 사람이 읽을 수 있다. 약관이 "민감하거나 기밀이거나 개인적인 정보는 보내지 말라"고 한다 | 개선에 쓰지 않는다(위반 감지용으로 잠깐 기록) |
| 한도 | 분당, 하루 요청 수가 있는데 공식 문서에 숫자가 없다. AI Studio 에서 본다. 질문 하나가 2~4번 요청한다 | 유료 등급 한도 |
| 켜는 일 | AI Studio 에서 키 만들기, Vercel 에 `CHAT_GEMINI_API_KEY` | 아래 1~7 |

A 로 켜면 광고 수익은 모델에 보내지 않는다(`ctx.redact`). 개인 단위 기록은 어느 길에서도 보내지 않는다.
둘 다 있으면 A 를 쓴다. 결제가 연결된 프로젝트의 계정이면 AI Studio 사용도 유료 약관(학습에 안 씀)을 따른다고 약관에 있다(2026-10-09 확인).

### B 켜는 순서

결제와 권한은 계정 일이라 사람이 한다.

1. Google Developer Program > My Benefits 에서 Google AI Pro 의 월 10달러 Cloud 크레딧을 결제 계정에 적용
2. 그 결제 계정에 연결된 GCP 프로젝트를 만든다(예: `dongsim-chat`). 챗봇 전용으로 두면 Spend Cap 이 다른 것을 건드리지 않는다
3. 그 프로젝트에서 Vertex AI API(`aiplatform.googleapis.com`)를 켠다
4. IAM 에서 지표 수집 서비스 계정(`GOOGLE_SERVICE_ACCOUNT_JSON` 의 `client_email`)에 "Vertex AI 사용자"(`roles/aiplatform.user`) 역할을 준다. 새 키를 만들지 않는다
5. 결제 > 예산 및 알림 > 예산 만들기 > 예산 유형 "Spend Cap": 그 프로젝트, 서비스 Gemini Enterprise Agent Platform, 월 8달러. 넘으면 몇 분 안에 새 요청이 막히고 다음 달 1일에 풀린다(미리보기 기능)
6. Vercel 환경변수 `CHAT_VERTEX_PROJECT` = 프로젝트 id (Production)
7. Supabase SQL Editor 에서 `supabase/migrations/0006_metrics_chat.sql` 실행

| `CHAT_MODEL` | `gemini-3.8-flash` | 생각은 low, 온도는 기본값. 구글 문서가 Gemini 3 은 1.0 아래로 내리면 반복이나 성능 저하가 생길 수 있다고 한다 |

| `CHAT_DAILY_LIMIT` | 30 | 사람당 하루 질문 수 |
| `CHAT_MONTHLY_USD` | 8 | 이번 달 추정 비용 합이 넘으면 막는다 |
| `CHAT_MOCK` | 없음 | `1` 이면 개발 서버에서만 가짜 모델(`devMock.ts`). 진짜 도구와 데이터로 화면과 검증 흐름을 본다. 질문에 "틀리게"를 넣으면 검증 실패 표시도 볼 수 있다 |

비용 상한은 두 겹이다. 프로젝트 Spend Cap 과 코드의 하루 질문 수, 월 비용 합. Spend Cap 이 미리보기라 바뀔 수 있어서 코드에서도 막는다.

## 비용

질문 하나는 보통 모델 2~4단계다. 2026-10-09 Gemini API 가격표로 3.8 Flash 보통 질문 약 0.026달러(추정)라 월 8달러면 약 300개.
실제 토큰은 `metrics_chat_log` 에 쌓이니 한 달 뒤 실측으로 이 문단을 고친다. 3.6~3.8 Flash 는 2027-01-01 에 가격이 두 배가 된다.

## 시험과 평가

- `pnpm test`: 검증기(`verify.test.mjs`: 인용한 가설 포함), 기간 풀이, 시험 판 가리기, 새 가입자 첫 판과 7일 비율, 추천 질문(`server.test.mjs`), 훑어보기 묶음과 움직인 칸, 비율 지표 %p, 받은 길, 가짜 모델 끝까지(`tools.test.mjs`), 근거 그림 고르기(`evidence.test.mjs`), 가짜 모델로 돌린 흐름(`run.test.mjs`: 한 번에 통과, 지어낸 숫자 다시 쓰기, 끝내 틀리면 표시, 원인 단정을 가설로, 도구 없이 숫자, 화면 기간)
- 2026-10-09 가짜 모델로 실제 데이터에 돌려 확인: 9월 App Store 최초 다운로드 80, Play 최초 설치 88, 서대페(9/19~20) 대 앞 주 같은 요일 App Store 44 대 1(표본 적음 표시)
- 이 시험으로 잡은 결함: 다시 쓰기 요청에 도구 결과가 빠졌다(`first.response.messages` 는 마지막 단계만 담는다). 고쳤고 시험을 더했다
- 연결 뒤 할 것: 골든 질문(단일 조회, 기간 비교, 행사, 원인 유도, 범위 밖, 아직 없는 데이터, 적은 표본)을 실제 모델로 돌려 숫자 일치, 거절, 원인 단정, 질문당 비용을 잰다. "아니에요" 피드백이 달린 질문을 골든 질문에 더한다

## 진짜 Gemini 로 돌린 평가 (`scripts/chat-eval`)

가짜 모델은 흐름이 맞는지만 보여 준다. 모델이 도구를 맞게 고르는지, 인용을 다는지, 원인을 단정하지 않는지는 진짜 모델로만 알 수 있어서, API 키 없이 구독(agy, Antigravity CLI)으로 돌리는 평가를 만들었다(2026-10-10).

- `mcp-server.mjs`: 운영과 같은 도구 7개를 MCP 로 연다. 실제 Supabase 를 읽기만 하고, 광고 수익은 보내지 않는다. 부를 때마다 toolCallId 를 붙여 기록한다
- `golden.mjs`: 골든 질문 15개. 숫자 정답 대신 맞는 도구와 기간, 비율의 %p, 볼 수 없는 것을 볼 수 없다고 하는지를 적었다(데이터가 날마다 바뀐다)
- `run.mjs`: 운영과 같은 지시문, 답 모양, 검증기로 채점한다. `--retry` 는 운영처럼 걸린 곳을 알려 주고 같은 대화에서 한 번 다시 쓰게 한다. `--rescore` 는 모델을 다시 부르지 않고 저장한 답을 지금 검증기로 다시 채점한다
- 준비와 실행 명령은 `run.mjs` 머리 주석에 있다. agy 에 MCP 서버를 등록하고, 그 서버 도구만 허용하는 규칙(`mcp(dongsim-metrics/*)`)을 넣어야 한다. 평가가 끝나면 둘 다 지운다

운영과 다른 점: agy 가 자기 에이전트 지시문을 앞에 붙이고 우리 지시문은 사용자 글로 들어간다. 그래서 토큰 수는 운영 비용 추정에 그대로 쓰지 않는다. 게임 서버 숫자는 어드민 토큰이 없어 비어 있다. 모델은 운영 기본값과 같은 Gemini 3.8 Flash(생각 낮음).

평가로 찾아 고친 것

| 찾은 것 | 고친 곳 |
| --- | --- |
| 표본이 적은 지표의 증감률을 % 로 말함(10건에서 39건을 "290% 늘었다") | 검증기가 잡게 했다. 다시 쓰게 하면 "개수와 차이로만 봤어요"로 고쳤다 |
| 단순한 비교에도 도구를 8~13번 부름(78초, 8.7만 토큰) | 지시문에 "필요한 만큼만, 같은 호출 반복 금지". 평균 5.5번에서 2.5번 |
| QR 링크 이동이 날짜별로 없어 주마다 합계를 7번 따로 조회 | 날짜별 열을 더했다(`downloadLinkClicks`). 주간 집계와 세 기간 모두 같다 |
| 답이 중간에 잘림 | 단계마다 결과를 모아 두고, 잘리면 도구 결과로 한 번 짧게 다시 쓰게 했다 |
| 두 결과의 숫자를 한 가설에 섞고 하나만 인용 | 숫자가 실제로 있는 결과를 코드가 인용에 더한다(10 이상만, 가설만) |
| 도구 결과의 2026-09-09 꼴 날짜를 그대로 옮김 | 서버가 "9월 9일"로 바꾼다 |
| 검증기 오탐: "GA4"의 4, "최근 28일"의 28, 주의점의 "3~7일"과 "10월 5일까지", 도구 없이 말한 "어제(10월 9일)" | 영문 이름 속 숫자와 기간 이름은 세지 않고, 주의점은 지시문 숫자를 허용하고, 도구 없는 답은 날짜를 빼고 본다. 사실 문장은 여전히 인용한 결과만 본다 |

잘한 것: "왜" 질문에 행사 날로 좁혀 앞 주 같은 요일과 비교하고, 사실에는 "함께 늘었다"까지만 쓰고, 같은 날 다른 행사가 겹쳐 효과를 나눌 수 없다고 스스로 짚었다. 비율은 "269회 중 15회, 5.6%, 2.5%p"처럼 규칙대로 말했다. 경쟁 앱, 예측, 가린 광고 수익, 비어 있는 게임 서버는 숫자를 지어내지 않고 볼 수 없다고 하면서 볼 수 있는 가까운 숫자를 알려 줬다.

남은 것: 애매한 질문("게시물 올린 주에 방문이 늘었어?")은 여전히 도구를 9~13번 부르고 1분 넘게 걸린다. 게임 서버 숫자(가입, 새 가입자 첫 게임)는 어드민 토큰이 있는 운영에서만 확인할 수 있다.

## 알려진 한계

- 질문 기록 표(`metrics_chat_log`)는 SQL Editor 에서 0006 마이그레이션을 실행해야 생긴다. 없으면 진짜 모델에서는 "기록 표가 아직 없어요" 안내로 멈추고(비용 상한을 셀 수 없다), 개발용 가짜 모델은 기록 없이 돈다(평가 버튼은 꺼진다)

- 검증은 숫자가 도구 결과 어딘가에 있는지만 본다. 결과 속 날짜의 "4"(10월 4일) 같은 작은 숫자와 우연히 같으면 통과할 수 있다
- 질문은 하나씩 따로 보낸다. 앞 질문을 기억하지 않아서, 이어 묻기는 기간이 들어간 후속 질문 칩으로 한다
- App Store 판매(한국 날짜와 맞음, #154 실측)와 App Store 분석(UTC)은 하루 경계가 달라 일 단위로 견주면 어긋날 수 있다

## 치즈 펫

지표 화면 아래를 돌아다니는 치즈 조각 캐릭터. 세계관의 "황금 치즈 조각"(copy-guide)이라 냥파와 도둥이 어느 편도 아니다.

- 그림: `scripts/pet/cheese.py` 가 코드로 그린다(28x28 칸, 7색). 고치면 `python scripts/pet/cheese.py <폴더>` 로 다시 뽑아 `cheese-sheet.png`, `.json` 을 `public/admin/pet/` 에 넣는다. 이미지 생성을 쓰지 않아 한도가 없고 프레임이 어긋나지 않는다
- 판단: `lib/admin/pet/brain.ts`(시험 `brain.test.mjs`). 한 번짜리 동작 > 챗봇이 건 기분 > 오래 가만히(30초 앉기, 2분 졸기) > 마우스 따라가기(멀면 달리기)
- 화면: `components/admin/pet/CheesePet.tsx`. 챗봇은 `petSignal()`(`lib/admin/pet/signal.ts`)로 알린다
- 움직임 줄이기 설정이면 걷지 않고 대기 첫 프레임만, 터치 기기는 따라가지 않는다
- 짧게 누르면 물어보기 패널이 열리고(손 흔들기), 꾹(0.25초) 누르면 들려서 따라오고 놓으면 떨어져 착지한다
- 패널을 가리지 않는다. 옆 패널이면 그 왼쪽까지만 다니고(덮이면 달려 나온다), 휴대폰의 아래 시트면 그 윗변에 올라선다. 패널은 `data-pet-avoid` 로 표시한다
- 치우려면 들고 있는 동안 오른쪽 아래에 나타나는 보관함에 넣는다. 상자 속에서 졸며 따라다니지 않고(새로고침해도 유지), 상자를 누르면 나온다. 물어보기 패널 아래 "치즈 보관함에 넣기 / 치즈 꺼내기"도 같은 일을 한다(키보드, WCAG 2.2.2)
- 닫기(×) 버튼은 두지 않는다. 눌려 사라진 뒤 다시 부르는 곳을 몰라 "아예 안 나온다"가 됐다
