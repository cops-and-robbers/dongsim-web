# 어드민 UI 설계 노트

관리자 화면을 만들면서 UI/UX로 고민하고 정한 것들을 남겨요. "왜 이렇게 했나"가 중심이에요.

## 무드

"테두리로 칸칸 나눈 전형적인 엔터프라이즈 어드민"은 피하고, 토스처럼 담백하고 정보가 또렷한 무드로 잡았어요. 여백과 색으로 정보를 나누고, 불필요한 선·박스는 줄였어요.

## 디자인 토큰 (라이트·다크 자동 대응)

색을 하드코딩하지 않고 시맨틱 토큰(`sd-*`)으로 썼어요. 라이트/다크에서 값이 자동으로 뒤집혀요.

- 액센트는 라이트=경찰=파랑, 다크=도둑=초록이에요. (두 진영이 대등한 우리 원칙 그대로요.)
- 상태색은 info(파랑)·positive(초록)·warning(앰버)·critical(빨강)으로 통일했어요.
- 표면·경계·글자는 surface / line / fg 계열로 묶었어요.

## 대시보드(개요) - "숫자 나열" 탈출

그냥 숫자만 늘어놓지 않으려고 했어요.

- 맨 위는 누구에게나 같은 공통 띠(진행 중 게임, 오늘 게임, 오늘 새 사용자, 전체 사용자)예요.
- 그 아래 "지금 할 일"은 처리를 기다리는 일만 모아요. 아래 "지금 할 일"에 규칙이 있어요.
- 그 아래 "내 지표"는 맡은 역할의 기본 카드예요. 자세한 규칙은 아래 "개요 카드"에 있어요.
- 게임이 없거나 유저가 없어도 빈 상태·스켈레톤이 항상 자리를 지켜요. (데이터가 없다고 레이아웃이 무너지지 않게요.)

## 색으로 상태를 말하기

카드 배경을 덕지덕지 칠하는 대신, 숫자·아이콘·문구의 색으로 상태를 전해요.

- **처리 대기(신고·버그)** = 빨강(critical). "확인이 필요해요"
- **0건(모두 처리)** = 파랑(info). "모두 처리됐어요" (대기=빨강 / 완료=파랑 대칭이에요.)
- **진행중 게임** = 액센트 카드
- 하늘색은 액센트(파랑)와 겹쳐서 안 썼어요. 파랑은 "주의"가 아니라 "정보"로 읽혀서요.
- 아이콘을 색 네모 박스에 가두지 않고 상태색만 입혔어요. 카드 색과 이중으로 튀지 않게요.

## 아이콘 - 손으로 그리지 않기

아이콘은 직접 그려서 어설프게 만들지 않고, 검증된 아이콘셋(Lucide) 원본 path를 그대로 가져와 stroke만 우리 셋에 맞췄어요.

- 개요 = `activity` (실시간 맥박 느낌)
- 게임 = `gamepad-2`
- 신고 = `siren` (경찰과 도둑 테마에 맞게요.)
- 버그 = `bug`

안드로이드·소셜 같은 브랜드 마크는 색 자체가 의미라 별도 파일로 관리해요.

## 화면 틀과 스크롤 (#180)

- **화면 틀은 둘이에요.** 표가 있는 목록은 `ListPage`(화면 높이에 맞추고 표 상자만 스크롤), 카드와 폼만 있는 화면은 `ScrollPage`(화면 전체가 스크롤)예요. 표 없는 화면에 `ListPage` 를 쓰면 아래가 잘리고 내려가지 않아요. 약관, 블로그 화면이 그랬어요
- **뒤 문서 잠금.** 어드민 셸은 공개 사이트 문서 위에 덮여 있어서, 잠그지 않으면 폰에서 끈 움직임이 뒤 문서로 넘어가 주소창이 접히고 셸이 튕겨요. 어드민에 있는 동안 html, body 스크롤을 잠그고(`AdminShell`), 스크롤 상자 끝에서 넘치는 움직임도 막아요(`overscroll-contain`)

## 운영 화면 원칙 (#217)

앱 설정, 온라인 게임처럼 실제 사용자에게 닿는 값을 바꾸는 화면(앞으로 출시, 스토어 페이지, 행사도)은 같은 방식으로 만들어요. 운영진이 개발을 몰라도 결과를 보고 고르고, 실수로 사용자를 막지 않게 하려는 거예요.

| 원칙 | 이렇게 해요 | 쓰는 틀 |
| --- | --- | --- |
| 결과 먼저 | 왼쪽에서 고르면 오른쪽에 저장 전 값으로 실제 화면을 그려요. 가짜 그림 대신 앱, 사이트의 실제 화면 코드를 옮겨 그려요 | `components/admin/ops/PreviewPane.tsx` (앱 설정, 온라인 게임) |
| 지금 상태 한눈에, 다음 할 일은 하나 | 화면 맨 위에 지금 상태, 그 아래 가장 먼저 할 일 하나만 크게 | (출시 화면에서 만들어요) |
| 바꾸기 전 전/후 확인 | 무엇이 어떻게 바뀌고 사용자에게 무슨 일이 생기는지 보여 줘요. 위험하면 빨간 버튼, 처음 초점은 취소 | `ChangeDialog` |
| 위험한 동작은 잠금 | 되돌리기 어려운 것(심사 제출, 출시, 강제 업데이트)은 잠금을 풀고 확인 문구를 직접 쳐야 눌려요. 서버가 누르는 순간 상태를 다시 읽어요 | (출시 화면에서 만들어요) |
| 시간은 우리 사용자 기준으로 | 사용자 절반이 해외예요(2026-08 ~ 11 첫 실행 기준 한국 52%, 미국 14%, 일본 8%, 호주 5%). 한국 밤은 유럽 오후, 미국 아침이라 시각을 고르는 칸 아래에 "그때 우리 사용자는 무엇을 하고 있나"를 보여 줘요 | `components/admin/ops/WorldClock.tsx`, `lib/admin/worldClock.ts`, `/api/admin/metrics/user-countries` |
| 실패는 쉬운 말로 | 무엇이 안 됐고 무엇을 하면 되는지. 외부 콘솔에서만 되는 일은 바로가기를 붙여요 | |
| 폰에서도 | 행사장에서 폰으로 고칠 수 있게 한 줄로 쌓여요 | |

### 나라별 시각 (`WorldClock`)

시각을 늘어놓거나 막대로 그리면 "그래서 지금 괜찮은가"는 사람이 계산해야 해요. 첫 시안(지역마다 하루 막대)은 읽는 법을 배워야 해서 버렸고, 결론 한 줄과 지역 칸으로 바꿨어요.

| 정한 것 | 이유 |
| --- | --- |
| 맨 위에 점 하나와 결론 한 줄. 겹치면 노란 점과 "**미국 동부, 호주**는 점검하는 동안 한창 노는 시간이라 쓰는 사람이 있을 수 있어요", 아니면 초록 점과 "사용자가 많은 지역은 모두 쉬는 시간이에요" | 결론부터 읽게. 무엇을 하라고 시키지 않고 사실만 말해요 |
| 결론에 이름을 올리는 건 비율 5% 이상인 지역만, 칸을 노랗게 칠하는 것도 같은 기준 | 1% 지역 하나 때문에 늘 노란 불이 켜지면 아무도 안 봐요. 문장과 칸 색이 같은 말을 하게 |
| 칸은 사용자가 많은 지역 6곳, 한국은 늘 첫 칸. 넓은 화면 3칸, 폰 2칸 | 최근 13주 새로 앱을 연 사람(테스트 기기 제외)을 나라별로 세어요(`/api/admin/metrics/user-countries`). 매일 쓰는 사람의 나라별 수는 아직 모으지 않아 이 기준을 칸 아래 적어요 |
| 칸 안에는 지역 이름과 비율, 해(아침 7시 ~ 밤 11시) 또는 달, "새벽 2:00", "저녁 7:00"처럼 말로 쓴 현지 시각, 날짜가 다르면 "전날", "다음 날" | 19:00 보다 "저녁 7:00"이 바로 읽혀요. 새벽 0 ~ 6, 아침 6 ~ 9, 오전 9 ~ 12, 낮 12 ~ 17, 저녁 17 ~ 21, 밤 21 ~ 24 |
| 한창 노는 시간은 현지 12 ~ 22시, 점검은 지금부터 끝나는 시각까지 15분 간격으로 겹치는지 봐요 | 2026-08 ~ 11 실제 게임 기록에서 한국 판은 12 ~ 21시, 해외 판은 현지 13 ~ 19시에 몰렸어요. 끝을 넉넉히 잡았어요 |
| 미국은 동부, 서부 두 칸으로 나누고 사용자를 반씩 | 3시간 차이라 한 칸이면 틀려요. 나라 안 지역은 몰라서 반씩 세요 |
| 시간대가 비슷한 나라는 한 칸(유럽은 파리, 동남아는 싱가포르 시간) | 칸이 너무 많아지지 않게 |
| 비율을 불러오는 동안은 회색 점과 주요 지역(한국, 일본, 미국 동서부, 영국, 호주)만, 칠하지 않아요. 못 불러오면 주요 지역 기준으로 판단하고 칸 아래에 그렇게 적어요 | 화면을 막지 않아요. 결론이 없는데 칸만 노랗게 뜨지 않게 |

서머타임은 시간대 이름으로 계산해요(`Intl`).

## 내비게이션 - 역할별 그룹

메뉴를 평평하게 두지 않고 역할로 묶고, 그룹 이름을 메뉴 위에 작게 적어요(2026-11-07, #211).

- 개요
- 데이터: 유저, 게임, 지표. 주로 조회하고 들어가 보는 곳이에요.
- 처리: 신고, 버그. 쌓이는 일이라 미처리 건수를 옆에 띄워요.
- 콘텐츠: 공지, 블로그, 동심지키미 소개, QR 인쇄물. 발행하거나 밖에 내보내는 것을 만드는 곳이에요.
- 운영: 출시, 앱 설정, 약관 재동의, 온라인 게임, 행사, 그림 보관함. 누르면 모든 사용자에게 바로 닿는 스위치예요.
- 팀: 일정, 변경 기록, 운영진. 서비스가 아니라 우리 팀을 다루는 곳이라 따로 묶어요. 일정은 팀이 한 일과 할 일(행사, 홍보, 출시, 테스트)이에요(#302). 변경 기록은 누가 무엇을 바꿨는지예요(#313).

### 사이드바 구조

메뉴가 11개로 늘면서 낮은 화면(노트북 브라우저 높이 약 650px)에서 아래 계정과 테마 줄이 화면 밖으로 밀렸어요. 메뉴 영역이 스크롤되지 않았기 때문이에요.

| 정한 것 | 이유 |
| --- | --- |
| 로고(위)와 계정 줄(아래)은 고정하고 가운데 메뉴만 스크롤 | shadcn Sidebar 와 Atlassian 내비게이션이 같은 세 칸 구조예요. 계정과 로그아웃은 어느 높이에서나 닿아야 해요 |
| 위로 스크롤하면 로고 아래 선, 아래에 더 있으면 끝을 흐리게 | 맥은 스크롤바를 숨겨서, 표시가 없으면 아래 메뉴가 있는 줄 몰라요 |
| 지금 메뉴는 보이는 곳까지 스크롤(흐림 높이만큼 여백) | 낮은 화면에서 아래쪽 메뉴로 들어와도 어디 있는지 보여야 해요 |
| 그룹 사이 선 대신 그룹 이름 | 이름이 있으면 열한 개를 다 읽지 않고 묶음으로 훑어요(디자인 시스템들의 그룹 제목 권고). 높이는 선과 거의 같아요 |
| 메뉴 한 줄 40px → 36px | 마우스로 쓰는 데스크톱이라 줄여도 누르기에 충분해요(WCAG 2.5.8 최소 24px). 남는 높이로 그룹 이름을 넣었어요 |
| 계정, 테마, 로그아웃을 한 줄로 | 자주 쓰지 않는 것들이라 한 줄이면 충분하고, 메뉴에 높이를 더 줘요 |
| 약관을 처리에서 운영으로, 이름은 화면 제목과 같은 "약관 재동의" | 쌓이는 일이 아니라 모든 사용자에게 닿는 실행이라 운영에 맞아요. 메뉴 이름이 화면 제목과 같아야 들어가서 헷갈리지 않아요. 폰 하단 탭은 칸이 좁아 "약관"으로 둬요 |
| 온라인 게임 아이콘을 지구본으로 | 게임 기록(게임패드)과 같은 아이콘이라 두 메뉴가 같은 것처럼 보였어요 |
| 온라인 게임이 점검 중이면 메뉴 옆에 "점검 중" | 앱 점검과 같은 까닭이에요. 켜 두고 잊으면 아무도 못 들어오는데 그 화면을 나가면 알 길이 없어요. 공개 전은 평소 상태라 띄우지 않아요 |
| 키보드 초점이 메뉴에 오면 파란 테두리 | Tab 으로 메뉴를 옮겨 다닐 때 어디 있는지 보여야 해요 |

접는 그룹이나 아이콘만 남기는 접힌 사이드바는 넣지 않았어요. 메뉴가 열한 개라 스크롤로 충분하고, 접으면 미처리 건수와 "점검 중"이 숨어요.

근거: [shadcn Sidebar](https://ui.shadcn.com/docs/components/sidebar)(머리, 바닥 고정과 가운데 스크롤), [Atlassian side navigation](https://atlassian.design/components/navigation-system/side-navigation)(바닥을 아래에 붙이는 스크롤 몸통).

## 목록은 돌아와도 그대로 (`lib/admin/useListParams.ts`)

유저, 게임, 지난 게임, 신고, 버그 목록의 필터와 페이지를 주소에 남겨요. 화면에는 아무것도 더하지 않아요.

| 정한 것 | 이유 |
| --- | --- |
| 값을 주소 하나에만 두고 읽어요 | 상태를 따로 들면 메뉴를 눌러 주소가 비었을 때 화면만 필터가 걸린 채로 남아요 |
| 메뉴를 누르면 새 목록, 상세의 "유저 목록"을 누르면 보던 목록 | 메뉴는 처음부터 보는 길, 상세의 링크는 돌아가는 길이에요. 그래서 마지막으로 본 주소를 이 탭 동안 기억해 둬요 |
| 필터를 바꿔도 방문 기록을 쌓지 않아요 | 쌓으면 뒤로 가기를 여러 번 눌러야 목록을 벗어나요 |
| 필터가 바뀌면 첫 페이지로, 없는 페이지면 마지막 페이지로 | 마지막 줄을 처리해 페이지가 사라지면 "아직 없어요"가 떠서 데이터가 없는 것처럼 보였어요 |
| 표 스크롤 위치도 되살려요 | 표는 안쪽 상자가 스크롤해서 브라우저가 대신 복원하지 않아요 |
| 새 목록이 올 때까지 이전 목록을 흐리게 둬요 | 필터를 누를 때마다 뼈대 화면으로 깜빡이지 않게 전부터 하던 방식을 지켰어요 |

근거는 Baymard 의 뒤로 가기, 필터 조사예요. 쇼핑 사이트 조사라 어드민에 옮긴 건 우리 판단이에요. 목록과 상세를 오가는 흐름이 같다고 봤어요.

## 최근 본 게임, 유저 (`components/admin/RecentViewed.tsx`)

게임 상세(열린 방, 지난 게임)와 유저 상세를 열면 기록해요. 찾는 길은 둘이에요. Ctrl+K 명령 창 맨 위(최근 5개)와 목록 필터 줄 끝의 시계 버튼(묶음마다 최근 10개)이에요.

| 정한 것 | 이유 |
| --- | --- |
| 시계 버튼은 눌러야 펼쳐져요 | 찾을 때만 쓰는 기능이라 평소엔 표 자리를 차지하지 않아요 |
| 게임 쪽 버튼은 열린 방과 지난 게임을 함께 보여 줘요 | 어드민은 "아까 본 그 게임"을 찾는 거라 어느 탭이었는지까지 기억하길 바라지 않았어요. 보조 줄의 "지난 게임"으로 구분해요 |
| 보조 줄은 상세 화면 제목 아래 글을 써요 | 초대코드만으로는 어떤 판인지 알기 어려워, 상세에서 본 글과 언제 봤는지로 알아봐요 |
| 브라우저에만 저장, 로그아웃하면 지워요 | 관리자 각자의 작업 기록이라 서버 없이 충분해요. 닉네임이 들어 있어 공용 PC 에 남기지 않아요. 대신 다른 기기와 이어지지 않아요 |
| 새 탭에서 연 상세도 함께 쌓여요 | 신고 상세의 닉네임 링크가 새 탭으로 열려요. 그래서 탭마다 따로인 저장소를 쓰지 않았어요 |
| 없어진 방, 탈퇴한 유저는 열어 보는 순간 기록에서 빠져요 | 방은 비면 삭제돼요. 다음부터 찾을 수 없는 항목을 보여 주지 않아요 |
| 명령 창에서 키보드로 옮기면 목록이 따라 내려가요 | 항목이 늘어 스크롤이 생겼어요. 마우스로 짚을 때는 움직이지 않아요 |

### 방금 보고 온 줄 (2026-11-07, #212)

개요의 표에서 마지막으로 열어 본 줄 하나만 왼쪽 파란 띠와 옅은 파란 바탕으로 표시해요. 대표 글자(초대코드, 닉네임)는 파란색이 돼요. 다른 줄을 열 때까지 남아요.

| 정한 것 | 이유 |
| --- | --- |
| 이미 본 줄 전부 대신 마지막 하나만 | 처음엔 메일함처럼 본 줄을 모두 회색으로 뒀어요. 게임 목록은 하나씩 처리하는 목록이 아니라 찾아보는 목록이라 몇 개만 열어도 회색이 쌓여 뜻을 잃었어요. 가장 많이 쓰는 운영자가 바꿔 달라고 했어요 |
| 회색 대신 파란 띠 | 회색은 "읽음, 끝남"으로 읽혀요. 게임은 상태가 계속 바뀌어서 회색이 "더 볼 것 없음"처럼 보였어요. 파란색은 "지금 여기"예요 |
| 종류마다 하나(열린 방, 지난 게임, 유저) | 목록마다 자기 줄 하나가 보여야 해요. 묶음으로 하나만 고르면 지난 게임을 본 뒤 열린 방 목록에는 표시가 없어요 |
| 상태 뱃지와 숫자는 그대로 | 표시는 위치만 알려 줘요. 최신 상태는 뱃지로 봐요 |
| 목록 스크롤 위치를 되살리는 것과 짝 | 돌아오면 그 줄이 바로 보여요 |
| 예전에 본 것은 시계 버튼과 Ctrl+K | 최근 10개, 5개를 그대로 보여 줘서 표시를 줄여도 잃는 기능이 없어요 |
| 기록은 묶음마다 30개 | 예전에는 본 줄을 모두 가리려고 300개였어요. 닉네임이 들어 있어 필요 이상 쌓지 않아요 |
| 다른 탭에서 연 것도 바로 반영 | 신고 상세의 닉네임은 새 탭으로 열려요. 돌아왔을 때 이미 표시돼 있어야 해요 |

브라우저 방문 기록(`:visited`)은 쓰지 않아요. 개인정보 보호 때문에 글자 색 정도만 바꿀 수 있고 줄 배경은 못 바꿔요. 로그아웃하면 기록과 함께 지워져요.

## 유저와 게임 두 칸 화면 (#315)

시안 "경도 어드민 유저와 게임"(어드민 페이지 설계 세션, 2026-11-10)을 옮겼어요. 왼쪽 목록은 그대로 두고 오른쪽에서 상세가 바뀌어요(`components/admin/split/`). 여러 명, 여러 판을 이어서 보는 일이 많아서 상세로 들어갔다 돌아오며 목록 위치를 잃는 단계를 없앴어요.

| 정한 것 | 이유 |
| --- | --- |
| 넓은 화면은 두 칸, 좁은 화면은 고른 것만 | 폰에서는 고르면 상세가 목록 자리를 차지하고 위에 "목록으로"가 붙어요 |
| 고른 것은 주소에 남겨요(`?u=`, `?room=`, `?h=`, `?q=`, `?f=`) | 새로 고치거나 팀원에게 주소를 보내도 같은 화면이 열려요 |
| 한 사람, 한 판만 담은 화면도 그대로 둬요(`/admin/users/[id]`, `/admin/games/[id]`, `/admin/games/history/[id]`) | 신고 화면처럼 다른 곳에서 링크로 열거나 부스에서 한 방만 띄울 때 써요. 상세 오른쪽 위 버튼으로 열어요 |
| 유저 검색을 맨 위에, `/` 로 바로 | 유저 화면에 오는 일 대부분이 신고나 문의에 나온 닉네임을 찾는 일이에요 |
| 유저는 가입한 날로, 끝난 판은 끝난 날로 묶어요 | 오늘 몇 명이 왔는지, 오늘 몇 판 했는지가 따로 세지 않아도 보여요. 다음 쪽에 같은 날이 더 있을 수 있는 마지막 묶음은 개수를 적지 않아요 |
| 유저 줄의 표시는 예외일 때만(운영자, 운영진, 위치 미동의) | 다 붙이면 눈에 걸리지 않아요 |
| 지금 방에 있는 사람은 초록 | 열린 방 명단과 맞춰 서버 추가 없이 알아요(`lib/admin/useLiveRooms.ts`). 신고 대상이 지금 게임 중인지가 가장 급해요 |
| 사람 그림은 앱 프로필 그림(냥파, 도둥이) 둘 중 하나를 유저 번호로 골라요 | 재미 요소예요. 앱과 같은 그림(`public/app-icons/profile_*.svg`)이라 모양이 낯설지 않고, 같은 사람은 어디서나 같은 그림이라 다시 찾기 쉬워요. 앱에서 실제로 고른 그림과는 상관없어서 백엔드 값을 따로 받지 않아요 |
| 유저 상세는 지금 방, 숫자 세 칸, 게임 기록, 계정 순서 | 운영진이 묻는 순서(지금 게임 중인가, 했나, 얼마나, 최근에도)예요. 계정과 운영진 스위치는 자주 안 봐서 아래에 둬요 |
| 승패 색 띠는 뺐어요 | 시안에는 최근 판을 색 칸으로 보여 주는 띠가 있었어요. 아래 목록과 같은 내용이고 범례를 읽어야 해서, 카드 제목 옆 "최근 20판 중 10승" 한 줄만 남겼어요 |
| 게임 목록은 열린 방과 끝난 판을 한 목록에 | 방은 하루 평균 4.6개라 열린 방만 보는 화면은 대부분 비어 있었어요. 열린 방이 맨 위예요 |
| 끝난 판 줄은 결과, 동네, 체포, 방장 순서 | 게임은 실제 장소에서 해서 위치가 판을 알아보는 가장 큰 단서고, 방장 이름이 두 번째 단서예요 |
| 거르기 칩은 끝난 이유만 | 서버가 `endReason` 하나로만 걸러요. 시안의 "이벤트" 칩은 받아 온 쪽만 걸러져 다 본 것처럼 보여서 뺐고, 줄의 "이벤트" 표시로 알아봐요. 기권은 경찰, 도둑으로 나눴어요 |
| 상세 맨 위는 위치 카드 | 지도 위에 동네 이름, 구역 크기, 감옥을 칩으로 얹어요(`components/admin/games/AreaCard.tsx`) |
| 방 상세는 지금 인원 숫자 다음 현장 운영 | 부스에서는 이 숫자를 보며 운영진 도둑을 더 넣을지 정해요 |
| 끝난 판의 경기 흐름은 나간 사람만 시간 막대에 | 서버에는 시작, 끝, 나간 시각만 있어요. 체포 시각은 기록되지 않아요 |
| 팀 기록은 막대나 점 대신 오른쪽 정렬 숫자, 칸 위에 "체포", "잡힘", "무전". 0은 흐리게, 무전을 안 쓴 경찰은 "안 씀", 값을 못 받았으면 "-" | 횟수가 대부분 0~3이라 막대는 1회뿐인 사람도 꽉 차 보였고, 도둑은 덜 잡힐수록 잘한 건데 길수록 잘한 것처럼 읽혔어요. 점은 세어야 읽히고 0과 큰 수에서 모양이 바뀌었어요. 숫자는 세로로 바로 비교되고, 0은 실제 결과라 지우지 않되 흐려서 0이 아닌 사람이 먼저 보여요 |
| 진행 시간은 "7분", 판 상세는 "14분 21초" | "7:00"은 옆의 끝난 시각("13:27")과 같은 모양이라 시각으로 읽혀요. 시계 모양은 "몇 시에"일 때만 써요 |
| 움직임: 상세 카드는 위에서부터 차례로 떠오르고(폰은 오른쪽에서 밀려 들어오고), 고른 줄 바탕과 거르기 칩은 미끄러져 옮겨 가고, 숫자 칸은 0에서 제 값까지 올라가요. 화면을 옮기면 본문이 흐림에서 또렷해지고, 어드민을 처음 열면 사이드바가 왼쪽에서 나오며 메뉴가 차례로 들어와요 | 운영진만 쓰는 화면이라 전환을 또렷하게 줘서 무엇이 바뀌었는지 눈이 따라가게 했어요. 모두 0.5초 안에 끝나고 나가는 움직임은 없어 누르자마자 바뀌어요. 끝나면 transform, filter 를 남기지 않아 안의 대화상자가 갇히지 않아요. 기기의 "동작 줄이기"를 켜면 바로 바뀌어요(`MotionConfig reducedMotion="user"`, globals.css `admin-detail-in`, `admin-nav-in`) |
| 목록은 끝에 닿으면 다음 쪽을 붙여요(`lib/admin/usePagedQuery.ts`) | 쪽 번호를 오가면 두 칸 화면의 목록 위치가 흔들려요. 버튼도 함께 둬서 키보드로도 불러와요 |
| Relay 레코드 id 에 타입 이름을 붙여요(`lib/relay/environment.ts`) | 게임 1번과 끝난 판 1번처럼 표마다 번호가 겹쳐요. 한 화면에 같이 들어오니 서로의 값을 덮어썼어요 |

알아 둘 것:

- 옛 주소 `/admin/games/history` 는 게임 목록으로 보내요
- 지난 판의 방장, 라운드, 시작 시각, 이벤트 여부는 운영(main)에 이미 있는 값이에요. 그 전 기록은 비어 있어서 빠지기만 해요
- 무전 시간과 동네 이름은 아래 "무전 사용 시간과 동네 이름"을 봐요

## 주로 플레이하는 국가 (#319)

해외 유저 문의가 오면 그 사람이 어느 나라에서 플레이하는지가 먼저 필요해요. 백엔드가 플레이 구역의 국가 코드와 유저별 플레이 국가를 내려 줘요(BE #241, `GameArea.countryCode`, `AdminGameSummary.countryCode`, `AdminUser.playCountries`). 국가는 플레이 구역에서 나온 값이라 국적이 아니에요.

| 어디에 | 무엇을 |
| --- | --- |
| 유저 목록 | 주로 플레이하는 국가가 한국이 아닐 때만 국기와 나라 이름 칩 |
| 유저 상세 | 숫자 세 칸 아래 "주로 플레이하는 국가": 국기, 이름, 몇 판 중 몇 판, 그 외 나라 두 곳까지, 아직 확인 중인 판 |
| 게임 목록 | 방과 판 둘째 줄 동네 이름 앞에 국기. 한국도 달아요 |
| 방, 판 상세 | 위치 카드의 동네 칩 앞에 국기 |

| 정한 것 | 이유 |
| --- | --- |
| 대표 국가는 가장 많이 한 나라, 같으면 최근 나라 | 서버가 이 순서로 줘요. 여러 나라를 늘어놓아도 대부분 한 나라라 정보가 늘지 않아요 |
| 목록에는 해외일 때만 | 다른 표시(운영자, 위치 미동의)처럼 예외일 때만 붙여야 눈에 걸려요 |
| 국기 이모지 대신 SVG(`flag-icons`, MIT) | 윈도우는 국기 이모지를 못 그려 "JP" 글자로 나와요. 화면에 뜬 나라의 그림만 받아요 |
| 국기 옆에 나라 이름 | 국기만으로는 낯선 나라를 못 알아보고, 색만으로 뜻을 전하지 않아요 |
| 장소 옆 국기는 한국도 늘, 유저 목록 칩은 해외일 때만 | 장소는 그 판의 속성이라 모든 줄에 같은 자리, 같은 모양이어야 해요. 해외만 달면 국기가 있다 없다 해서 같은 칸이 들쭉날쭉해 보여요. 유저 목록 칩은 운영자, 위치 미동의처럼 눈에 걸려야 하는 예외 표시라 다 붙이면 아무것도 눈에 걸리지 않아요. 상세에서는 한국도 국기와 이름으로 보여요 |
| 이름은 브라우저 `Intl.DisplayNames` | 처음 보는 나라도 한국어 이름이 나와요. "오스트레일리아", "홍콩(중국 특별행정구)"처럼 긴 것만 바꿔요(`lib/admin/country.ts`) |
| 국가를 아직 못 찾은 판은 "확인 중 n판" | 서버는 처음 보는 곳을 한 번에 5곳까지만 찾아요. 숫자가 틀려 보이지 않게 따로 세요 |

알아 둘 것:

- 운영 배포는 개인정보 처리방침과 위치정보 이용약관 개정(위탁, 국외 이전, 게임 기록 항목과 목적) 시행 뒤에 해요. 주소 변환에 게임 구역 좌표가 새로 나가기 때문이에요
- 다른 백엔드 값처럼 따로 읽어서, 백엔드가 나가기 전에는 국가 표시만 빠져요
- 로컬 목업은 아홉에 하나가 주로 일본, 그 밖에 미국, 호주, 확인 중인 판이 섞여요. 유저 4번은 배포 전처럼 답해요

## 유저 상세의 방과 끝난 게임 (`components/admin/users/UserPanel.tsx`, #202)

예전 "참여 게임 이력" 카드는 지금 들어가 있는 방만 보여 줬어요(`participations`). 방을 나가면 줄이 사라져서 이력처럼 읽히면 틀려요. 백엔드가 끝난 판 기록을 `gameHistories` 로 내려 주면서(BE #227) 둘을 나눴어요.

| 정한 것 | 이유 |
| --- | --- |
| 탭 없이 카드 두 개를 위아래로 | 둘을 같이 봐야 "지금 어디 있고 전에 뭘 했나"가 이어져요. 탭으로 나누면 오가며 기억해야 해요(NN/g "Tabs, Used Right") |
| 지금 들어가 있는 방을 위에 | 줄이 적고, 지금 벌어지는 일이 먼저예요. 판이 끝나도 방을 나가기 전까지 위에 남아서 카드 아래에 적어 뒀어요 |
| 끝난 게임은 조회를 나눠요(`AdminUserGameHistories`) | 운영 서버에 필드가 없으면 스키마 검사가 쿼리 전체를 거절해요. 한 쿼리에 넣으면 유저 상세가 통째로 안 열려요. 나누면 이 카드만 "서버 업데이트가 끝나면"으로 안내해요. 게임 상세의 이벤트 스위치(#178)와 같은 방식이에요 |
| 줄을 누르면 지난 게임 상세(`gameResultId`) | 방은 비면 지워지고 한 방에서 여러 판을 해서 `gameId` 로는 그 판을 찾을 수 없어요. 지금 들어가 있는 방은 방이 있으니 그대로 게임 상세로 가요 |
| 줄을 누르면 그 판이 오른쪽에 열려요 | 두 칸 화면에서는 `/admin/games?h=` 로, 한 사람 화면에서는 판 화면으로 가요 |
| 결과는 승리, 패배, 중도 퇴장 | 판이 끝나기 전에 나갔으면 팀이 이겼어도 승리로 적지 않아요 |
| 승패를 색이 아니라 글자로 | 색만으로 뜻을 전하지 않아요(WCAG 1.4.1). 초록, 파랑은 도둑, 경찰 뱃지가 이미 쓰고 있어 승패 색으로 쓰면 헷갈려요 |
| 처음 20판, 버튼을 누르면 100판까지 | 백엔드가 건너뛰기와 전체 개수를 주지 않아 쪽 번호를 만들 수 없어요. 한 목록이 이어지는 더 보기를 썼어요(Baymard 조사. 쇼핑 사이트 조사라 옮긴 건 우리 판단이에요) |
| 처음엔 21판을 물어요 | 20판만 물으면 딱 20판인 유저에게도 눌러도 늘지 않는 버튼이 생겨요. 100판을 채우면 그 뒤를 알 수 없어 "최근 100판"이라고 적어요 |
| 빈 목록, 불러오는 중, 실패를 다르게 | 비어 있는 것과 불러오는 중, 실패를 헷갈리면 안 돼요(NN/g 빈 상태 지침). 있던 줄을 다시 받다 실패하면 줄을 지우지 않아요. 더 보기를 누른 뒤에는 버튼 글자로 불러오는 중임을 알려요 |
| 유저 상세는 30초마다 뒤에서 읽고, 실패하면 보던 화면을 둬요(#205) | `fetchKey` 로 다시 읽으면 Relay 가 실패를 기억했다가 다음 그릴 때 던져서 잠깐의 끊김에 화면 전체가 오류로 바뀌어요. 그래서 `fetchQuery` 로 스토어만 바꿔요 |
| 끝난 게임은 60초마다 읽어요(#205) | 판이 끝날 때만 늘어나서 1분이면 충분해요. 배포 전에도 이 간격으로 물어서 릴리즈되면 새로고침 없이 나와요 |
| 배포 전 안내는 그 필드가 없다는 오류일 때만(#205, `lib/admin/notDeployed.ts`) | 흔한 오류까지 "따로 할 일은 없어요"로 안내하면 장애인 줄 모르고 기다려요. 그래서 필드 이름까지 봐요 |
| 기록이 8월 14일 밤부터라고 늘 적어요 | 그 전에 가입한 유저도 "끝난 게임 기록이 없어요"가 나올 수 있어요. 게임을 안 했다고 오해하면 안 돼요 |
| 2026-09-17 전에 끝난 판의 기록 칸은 "-" | 체포, 잡힘 횟수는 v3.9.0 부터 쌓였고 그 전 값은 기본값 0 이에요. 실제로 0 번과 구분되지 않아요 |

알아 둘 것:

- 탈퇴하면 유저 행이 지워져서 이 화면 자체가 열리지 않아요. 카드의 빈 목록은 탈퇴와 상관없어요(기록은 익명으로 남아요)
- 이벤트 게임에서 나갔다 다시 들어오면 마지막 입장의 팀과 횟수만 와요. 판 전체는 지난 게임 상세에서 봐요
- MVP 는 백엔드가 뽑은 값(v3.10.0 부터)이에요. 지난 게임 상세는 화면에서 따로 계산해서 동률이면 다를 수 있어요
- 방장, 이벤트 표시는 v3.10.0 전 판에는 없어요
- 8월 14일과 9월 17일 기준은 운영 날짜예요. 개발 서버는 값이 조금 일찍 쌓였어도 같은 기준으로 보여요. 운영 화면이 맞는 게 중요해서 서버별로 나누지 않았어요
- 지난 게임 목록은 백엔드가 `createdAt`(시작 시각에 가까운 값)으로 정렬해요. 자정을 넘긴 판은 종료일 순서가 살짝 어긋나 보일 수 있어요. 고치려면 백엔드 정렬을 바꿔야 해요
- 종료 시각은 지난 게임 목록, 상세와 같은 값이에요. 지난 게임 쪽은 `endedAt` 이 비어 있는 옛 기록에 `createdAt` 을 쓰고(`gameEndedAt`), 유저 상세는 `createdAt` 을 받지 않아 "기록 보기"로 적어요

## 메뉴의 미처리 건수 (`lib/admin/usePendingCounts.ts`)

| 정한 것 | 이유 |
| --- | --- |
| 신고, 버그 옆에 숫자만, 0건이면 아무것도 없어요 | 늘 보이는 자리라 빨간 동그라미를 달면 눈이 계속 가요. 끼어드는 알림은 하던 일로 돌아오는 데 시간이 걸린다는 조사가 있어서(Iqbal, Horvitz 2007), 필요할 때 눈으로 확인하는 정도로 뒀어요 |
| 탭 제목 앞에 `(3)` | 다른 탭에서 일할 때 보여요. 그래서 탭이 숨어 있어도 5분에 한 번은 읽어요. 보고 있을 때는 30초마다 읽어요 |
| 신고, 버그를 저장하면 바로 다시 읽어요 | 처리했는데 숫자가 그대로면 저장이 안 된 것처럼 보여요 |
| 큰 숫자는 `99+` | 메뉴 폭이 좁고, 그 이상은 얼마인지보다 많다는 게 중요해요 |
| 읽기에 실패하면 마지막 숫자를 그대로 둬요 | 숫자 때문에 메뉴가 깨지면 안 돼요 |

신고 건수는 통합 신고(`adminAllReports`)에서 세요. `adminDashboard.pendingReportCount` 는 게임 채팅 신고만 세서 모집글, 커뮤니티 채팅 신고가 빠져요. 개요 화면도 같은 값으로 바꿨어요.

## 앱 설정 (`app/(ko)/admin/app-config/page.tsx`)

앱을 다시 배포하지 않고 바꾸는 Firebase Remote Config 값을 어드민에서 다뤄요. 값 이름과 규칙은 `lib/admin/appConfig.ts`, Firebase 호출은 `lib/admin/server/remoteConfig.ts` 예요. 콘솔을 없애는 게 아니라 평소 쓰는 11개만 안전하게 옮긴 거예요. 조건, 단계별 출시, 되돌리기는 콘솔에서 해요.

### 개발을 몰라도 쓸 수 있게

| 정한 것 | 이유 |
| --- | --- |
| 왼쪽 설정, 오른쪽 폰(`components/admin/appConfig/AppPreview.tsx`) | 값 이름만 봐서는 앱 어디가 바뀌는지 알 수 없어요. 저장 전 값을 실제 앱 화면으로 바로 보여 줘요. 화면은 사이트 데모의 장면과 앱 코드를 옮겼어요 |
| 폰은 창 높이 안에 들어오게 줄여요 | 폰 영역이 창보다 크면 끝에 닿아, 선택지를 바꿔 저장 줄이 생길 때마다 폰이 65px씩 움직이고 위쪽이 잘렸어요. 고치는 값과 결과를 함께 봐야 하니 폰이 제자리에 있어야 해요 |
| 폰 안을 눌러 볼 수 있어요 | 배너를 누르면 어디로 가는지, "나중에"를 누르면 어떻게 되는지 직접 따라가요. 버전은 예시 버전을 골라 그 앱으로 열면 어떻게 되는지 봐요 |
| 값이 나오는 자리에 파란 테두리 | 앱에는 없는 관리자용 표시예요. 화면 전체 중 어디가 이 값인지 찾지 않아도 돼요 |
| 점검, 앱 버전, 광고, 홈 배너, 이벤트 게임 탭 | 값 14개를 늘어놓지 않고 하려는 일로 나눠요. 탭을 옮겨도 쓰던 입력은 남아요 |
| 점검이 꺼져 있는데 지난 시각이 남아 있으면 지우기 버튼 | 콘솔로 점검하던 때의 날짜가 남아 있어요. 사용자에게 보이지 않아 연결을 처음 시험할 때도 이 값으로 해요 |
| 탭마다 맨 위에 "언제 쓰는지" 한 문장, 점검은 "시작하면 이렇게 돼요" | 처음 쓰는 사람도 누르기 전에 결과를 알아요. 내용은 앱 코드에서 확인한 동작만 적어요 |

### 값마다 다르게 다뤄요

| 값 | 다루는 법 | 이유 |
| --- | --- | --- |
| 점검 | 스위치가 아니라 "점검 시작", "점검 끝내기" 버튼 | 사용자 전체를 막는 일이라 다른 설정처럼 생기면 안 돼요 |
| 점검 시작 | 빨간 버튼, 처음 초점은 취소, 끝나는 시각은 비워 두고 시작 | 2026-11-01 점검 때 9월 날짜 문구가 그대로 나갔어요. 예전 값을 채워 두지 않아요 |
| 끝나는 시각 | 글을 받지 않고 "안 적기, 1시간 뒤, 2시간 뒤, 직접 고르기" 중에 골라요. 직접 고르면 달력과 30분 간격 시간 목록을 열어요 | 이 값은 번역되지 않고 모든 언어로 그대로 나가요. 고르게 하면 `~ 2026-11-03 01:00 (KST)` 한 형식이 되고, 오타와 지난 시각을 막아요. 장애 때는 버튼 한 번이면 돼요. 고르면 아래에 지금부터 끝나는 시각까지 사용자가 많은 지역 중 한창 노는 시간과 겹치는 곳이 있는지 보여 줘요(#217) |
| 점검 끝내기 | 일반 버튼, 끝나는 시각도 함께 지움 | 복구는 막지 않아요. 지워야 다음 점검에 낡은 날짜가 안 남아요 |
| 강제 업데이트, 배너 표시 | 켜짐/꺼짐 글자 대신 결과를 적은 선택지 | 무슨 일이 생기는지 고르면서 읽혀요 |
| 최소 버전 올리기(강제 업데이트 켜짐) | 빨간 버튼과 "3.2.1보다 낮은 앱은 쓸 수 없어요" | 되돌려도 그사이 사람들은 이미 막혀요 |
| 전체 광고 끄기 | 빨간 버튼과 경고 | 수익에 바로 영향이 있어요 |
| 나머지 | 이전 값과 새 값만 확인 | 위험하지 않은데 빨갛게 하면 진짜 위험할 때 안 읽어요(NN/g) |

타이핑해서 확인하는 방식은 쓰지 않았어요. 장애 때 점검을 빠르게 켜야 하는데 글자를 치게 하면 방해가 돼요. 빨간 버튼, 취소에 먼저 가는 초점, 결과를 적은 문장으로 충분하다고 판단했어요.

### 실수를 막는 장치

| 장치 | 막는 일 |
| --- | --- |
| 서버가 11개만 받고 최신 템플릿에 합쳐요 | Firebase 는 전체를 덮어써요. 콘솔에서 더한 값, 설명, 조건이 지워지지 않아요 |
| 켜짐/꺼짐은 고르게만 하고 서버도 `true`, `false` 만 받아요 | 앱이 쓰는 Flutter SDK 는 `true`, `1` 만 켜짐으로 읽어요(대소문자 무시). `ture`, `yes`, `on` 은 오류 없이 꺼짐이 돼요. 콘솔에 `TRUE` 처럼 적힌 값도 화면이 앱과 똑같이 읽어요 |
| 버전은 숫자 칸 세 개(`components/admin/appConfig/fields.tsx`) | `3.2.x`, `3.2` 를 칠 수 없어요. 점을 치면 다음 칸, 위아래 화살표는 1씩, `3.2.7` 을 붙여 넣으면 나눠 들어가요 |
| 앱스토어보다 높은 버전을 고르면 경고 | 없는 버전으로 업데이트를 권하거나 막게 돼요. 조회가 늦을 수 있고 플레이 스토어는 볼 길이 없어 막지는 않아요 |
| 배너 이미지는 주소를 치지 않고 파일을 올려요(`BannerImagePicker`) | 틀린 주소를 넣으면 앱이 배너를 말없이 숨겨요. 서버도 우리 `banners/` 폴더 주소만 받아요. 폴더 목록은 고를 일이 없어 보여 주지 않아요 |
| 권장 크기 1444 × 272px, 글자와 얼굴은 가운데 1364 × 160px | 앱 코드로 계산했어요(`BANNER_SIZE`). 폰은 비율이 거의 같지만 iPhone SE 는 위아래 9%, iPad 는 위아래 19%가 잘려요. 점선으로 보여 주고, 올린 파일이 벗어나면 어느 쪽이 잘리는지 알려 줘요. 기기로 재 본 값은 아니에요 |
| 올릴 때 파일 앞부분으로 종류 확인, 2MB 제한, 이름은 서버가 지어요 | 덮어쓰기로 지금 나가는 이미지가 바뀌면 안 돼요. 올려도 적용 전에는 앱에 안 나가요. 삭제 기능은 일부러 없어요 |
| 링크는 `https://` 가 칸 밖에 고정 | 다른 방식의 주소를 칠 수 없어요. "열어 보기"로 저장 전에 확인해요 |
| 버전 형식과 "최소 버전은 최신 버전 이하"를 화면과 서버가 둘 다 검사 | 앱은 `3.2.x` 의 틀린 자리를 0 으로 읽고 넘어가서 조용히 틀려요 |
| 증거 사진도 파일로 올려요(`EvidenceImagePicker`) | 서버는 우리 `evidence/` 폴더 주소만 받아요. 앱이 디스크에 저장하지 않고 켤 때마다 받아서 배너보다 작은 1MB까지만 받아요 |
| 증거 사진 수는 값으로 두지 않아요 | 앱은 앞에서부터 빈 값을 만나기 전까지만 사진으로 봐요. "2장인데 주소는 1개" 같은 어긋남이 없어요. 건너뛴 번호는 저장을 막아요 |
| 증거 사진 비율은 9:16에서 16:9, 사진끼리 같게, 긴 쪽 2400px 아래 | 칸 크기를 사진 비율로 정해서, 다르면 칸 안에 여백이 생겨요. 앱은 원본 크기로 펼치니 해상도도 막아요. 범위 밖은 올리기 전에, 서로 다르거나 불러오지 못한 사진은 적용 전에 막아요 |
| 켜진 배너는 이미지 필수 | 앱은 이미지가 없는 배너를 말없이 숨겨서 아무도 모르고 지나가요 |
| ETag 비교 후 게시 | 화면을 본 뒤 다른 사람이 바꿨으면 게시하지 않고 최신 값을 다시 보여 줘요 |
| 먼저 `validateOnly` 로 검사 | Firebase 가 거부할 내용을 실제 게시 전에 잡아요 |
| 값이 바뀌면 쓰던 입력을 버려요 | 낡은 값 위에 고치지 않아요 |
| 콘솔에서 조건이 걸린 값은 잠가요 | 한 값으로 보여 줄 수 없는 값을 덮어쓰지 않아요 |
| 메뉴에 "점검 중" | 화면을 나가도 켜 둔 걸 잊지 않아요(5분마다, 저장 직후 확인) |
| 버전 설명에 "이름: 무엇을 무엇으로" | 서비스 계정으로 게시하면 Firebase 에는 그 계정만 남아요. 이름은 화면이 보낸 값이 아니라 토큰으로 백엔드에 물어요 |

### 실제 사용자에게 닿지 않게

Firebase 프로젝트가 하나뿐이라 잘못하면 개발 중에 실제 값이 바뀌어요. 그래서 두 겹으로 막아요.

1. 로컬(`pnpm dev`)은 MSW 가 가짜 값으로 답해서 Firebase 에 닿지 않아요(`lib/admin-mock/appConfig.ts`). 화면에 테스트 값이라고 적어요.
2. 서버 경로는 `VERCEL_ENV === "production"` 일 때만 저장해요. 미리보기 배포는 볼 수만 있어요.

### 언제 적용되나요

새 버전 앱(FE #666)은 켜져 있는 동안 어느 화면에서든 게시 신호를 받아 바로 반영해요. 점검이 켜지면 바로 점검 화면으로 보내되 게임과 글쓰기는 끊지 않고 그 화면에서 나올 때 막아요. 점검이 꺼지면 앱을 다시 열지 않아도 돌아와요. 끝나는 시각은 보여 주는 글자일 뿐이라 저절로 풀리지 않아요.

옛 버전 앱은 시작 화면에서 값을 읽고 릴리스 빌드는 최소 1시간 간격으로 새로 받아요. 그래서 다시 열 때 적용되고 최대 1시간 늦을 수 있어, 화면에 두 경우를 함께 적어요. 버전 값은 어떤 앱이든 앱을 열 때만 판단해요. 

스위치는 누르면 바로 바뀌는 부품이라(NN/g) 광고는 누르는 즉시 확인창을 열고, 저장 버튼을 두지 않아요. 버전과 배너는 함께 고치는 값이라 입력 후 "변경 내용 확인"을 눌러요. 폰에서는 하단 탭이 이미 9칸이라 상단 헤더 아이콘으로 들어가요.

### 처음 연결하기

1. Google Cloud 프로젝트 `copsandrobbers-8c026` 에서 Firebase Remote Config API 가 켜져 있는지 보고, 앱 설정 전용 서비스 계정을 만들어요. 지표 수집 계정과 나눠요.
2. 그 계정에 Firebase Remote Config 관리자(`roles/cloudconfig.admin`) 역할을 주고, Storage 버킷에는 저장소 개체 생성자(`roles/storage.objectCreator`)만 있으면 돼요. 지금 계정에는 저장소 개체 뷰어도 들어가 있는데, 그대로 둬도 괜찮아요. 지우는 권한은 주지 않아요.
3. JSON 키를 Vercel 환경변수 `REMOTE_CONFIG_SERVICE_ACCOUNT_JSON` 에 넣어요(Production 만). `.env.local` 에는 넣지 않아요.

### 온라인 게임 모니터링 (`app/(ko)/admin/webgame/monitor/page.tsx`, #223)

"운영 상태"와 "모니터링" 두 탭으로 나눠요. 상태를 바꾸는 일과 판을 지켜보는 일은 하는 순간이 달라서예요(게임 메뉴의 열린 방, 지난 게임과 같은 모양).

무엇을 보여 줄지는 Google SRE 책 "Monitoring Distributed Systems"의 네 가지 신호(지연, 트래픽, 오류, 포화)에 맞췄어요.

| 신호 | 화면 | 재료 |
| --- | --- | --- |
| 지연 | 최근 왕복 시간, 판마다 사람별 왕복 시간(중간, 느린 5%, 가장 느린) | 게임 서버 판 결과의 `net`(폰이 2초마다 잰 값) |
| 트래픽 | 지금 도는 판, 오늘 끝난 판, 최근 24시간 시간대별 판 수 | `/live`, 판 결과 |
| 오류 | 판마다 다시 연결한 횟수, 끝난 이유(모두 나감 등) | 판 결과 |
| 포화 | 오늘 사용량(무료 한도 대비, 자동 배포가 멈추는 70% 선), 서버 계산 간격이 밀린 횟수 | Cloudflare 통계, 판 결과의 `tick` |

| 정한 것 | 이유 |
| --- | --- |
| 비용이 드는 로그 저장은 쓰지 않아요 | Cloudflare 로그 저장은 받은 메시지마다 한 줄이라 몇 판 만에 무료 한도를 넘어요. 판 결과 한 줄(이미 있음), `/live`, 통계 조회(무료)로 충분해요 |
| 사용량은 자동 배포 검사와 같은 계산 | 계정 전체의 Worker 요청과 Durable Object 요청을 더하고, 실행량은 GB-s 로 봐요(게임 `tools/usage-guard.mjs`). 화면의 70% 선이 배포가 멈추는 선과 같아야 해요 |
| 시간대별 그래프는 판 결과로 그려요 | Cloudflare 시간대 통계는 계정의 다른 서비스가 섞여요. 우리 판만 세려면 판 결과가 정확해요 |
| 한 색 세로 막대, 범례 없음, 판 수는 막대 위에 바로 | 값이 한 가지라 제목이 이름을 맡아요. 막대는 바닥에 붙이고 위만 둥글게, 사이 2px(차트 규칙). 판이 없는 시간은 바닥 눈금만, 24시간 내내 없으면 막대 대신 그렇다고 적어요. 판 수가 있는 막대에만 숫자를 붙여 마우스를 올리지 않아도 읽혀요. 올리면 그 시간도 함께 떠요 |
| 문제 표시는 알약에 글자로 | 왕복 0.25초 이상 "느림"(주황), 0.5초 이상 빨강, 다시 연결 "끊김 N번", 계산 간격 0.1초 초과 "서버 밀림 N번". 색만으로 알리지 않아요. 0.25초와 0.5초는 손으로 쫓고 잡는 게임이라 조작이 밀린다고 느끼는 선으로 팀이 정한 값이에요 |
| 줄을 누르면 사람별로 펼쳐요 | 목록에서는 판 단위로 훑고, 원인을 볼 때만 사람별 숫자를 봐요. 이름과 캐릭터 번호는 게임 서버가 남기지 않아 편만 보여요 |
| 보는 동안 30초마다 다시 읽고, 칸마다 따로 실패 | 판 결과를 못 읽어도 사용량은 보여요. 통계 조회는 5분에 300번까지라 서버 경로가 1분 동안 같은 값을 나눠 써요 |

| 숫자 셋은 한 카드에 나란히(`StatStrip`), 숫자 옆에 단위("판", "ms") | 카드 셋보다 덜 시끄럽고, 폰에서도 한 줄이라 세로로 길게 쌓이지 않아요. 왕복 시간 아래에는 "최근 10판 기준, 괜찮아요/느려요/아주 느려요"를 글자와 색으로 |
| 오른쪽 위 "HH:MM:SS 기준"과 다시 불러오기 버튼 | 30초마다 바뀌는 화면이라 언제 값인지 보여야 해요. 다시 못 불러오면 지난 값을 지우지 않고 그 시각을 알려요 |
| 사용량: 큰 % 먼저, 실제 수와 한도는 아래 작게, 70% 선 위에 "70%" | 먼저 읽을 것을 크게. 선을 넘으면 노랑과 함께 "N시간 M분 뒤 다시 배포할 수 있어요"(다음 UTC 0시까지)로 다음에 할 일을 알려요 |
| 판 목록: "전체 N / 살펴볼 판 M" 거르기, 처음 20판, "더 보기" | 200판을 한 번에 그리면 길고 느려요. 기준은 "살펴볼 판 기준" 툴팁에 글로 |
| 시각은 "오늘 01:34", "어제 16:40", 그 전은 "11.05 12:00" | 날짜를 계산하지 않고 읽혀요(한국 시간) |
| 느린 값은 칸 안에서도 노랑과 빨강, 굵게 | 펼친 사람별 표에서 어느 사람이 느렸는지 바로 보여요. 같은 줄의 알약 글자가 뜻을 말해서 색만으로 알리지 않아요 |
| 폰: 판마다 세 줄(결과와 시각, 알약, 인원과 걸린 시간과 왕복), 사람별 표는 사람마다 한 줄 | 표가 옆으로 넘치면 알약이 화면 밖으로 밀려요 |

연결: Vercel Production 환경 변수 `CLOUDFLARE_ANALYTICS_TOKEN`(Cloudflare 사용자 지정 토큰, 권한은 "계정 > 계정 분석 > 읽기" 하나)과 `CLOUDFLARE_ACCOUNT_ID`(계정 번호)를 넣어요. 없으면 사용량 칸에 연결 안내만 떠요. 판 결과는 이미 있는 `WEBGAME_ADMIN_KEY` 로 읽어요.

## 행사 (`app/(ko)/admin/events`, #219)

행사 때 사용자가 보는 곳(포토부스 `/photobooth`, 홈 팝업, 행사 이야기 페이지 `/event`, 홈 미니게임 칸)의 값을 행사 하나로 묶어 재배포 없이 바꿔요.
예전에는 Vercel 환경 변수(`NEXT_PUBLIC_PHOTOBOOTH_*`)와 코드에 흩어져 있어 행사마다 고치고 다시 배포했어요.

행사는 일정(어드민 "일정")에서 성격을 "행사"로 둔 날이에요. 여기서 새로 만들지 않아요(같은 일정을 두 곳에서 만들면 갈려요). 끝난 행사의 "성적표 보기"는 일정 화면에서 그 행사 날을 열어요(`/admin/schedule?day=`).

### 값이 흐르는 길

```
어드민 저장 → Supabase event_settings(행사마다 한 줄, 저장본은 event_settings_history)
  → lib/event/server.ts 가 "지금 행사"를 골라 30초 묶어 읽음(저장하면 바로 버림)
  → /photobooth, 사진 올리기, /event, 홈 팝업, 홈 미니게임 칸, 공유 카드(OG)
```

- 지금 행사: 부스 운영 시간 안인 행사 → 아직 안 끝난 행사 중 가장 먼저 여는 것 → 가장 최근에 끝난 것(감사 화면). 홈 팝업은 지금 떠 있어야 할 것 중 행사 날이 가까운 것
- 저장소를 못 읽거나 저장한 행사가 없으면 마지막으로 코드에 있던 값(7/4 서울 게임 타운, `LEGACY_SETTINGS`)으로 돌아요. 행사 중에 저장소가 멈춰도 부스가 서요
- 홈은 1분마다 다시 그려요(`revalidate = 60`). 부스와 /event 는 요청마다 읽어요
- 홈 팝업 "다시 보지 않기"는 행사 id 로 기억해요. 예전 키는 행사 이름이 박혀 다음 행사에 안 떴어요
- 홈 미니게임 칸은 사이트 설정 하나(`site_settings.home_minigame`)예요. 비어 있으면 숨겨요. `/play` 주소는 늘 열려 있어요

### 포토부스 탭 (#221)

행사마다 장비와 성격이 달라서(포토프린터가 있는 곳, QR로만 받는 곳, 줄이 긴 축제) 부스 흐름과 문구를 행사마다 정해요.
값은 행사 설정의 `kiosk` 칸(`lib/event/kiosk.ts`)이고, 키오스크와 사진 받기(`/p`)가 읽어요.

| 정한 것 | 이유 |

| 맨 위에서 부스 방식(인쇄 부스, QR 부스, 빠른 부스)을 고르면 아래 값이 채워지고, 하나씩 바꿀 수 있어요 | 같은 성격의 행사도 장비가 달라 "행사 종류"가 아니라 "부스 방식"으로 시작값을 둬요. 지난 행사에서 통째로 가져오기는 지난 행사 이름이 남은 문구를 같이 옮겨 와 넣지 않았어요 |
| 왼쪽에 손님이 거치는 화면(시작, 찍기, 고르기, 미리보기, 받기 / 준비 중, 끝난 뒤 / 손님 폰), 가운데에 그 화면, 오른쪽에 그 화면에서 바꿀 수 있는 것만 | Shopify 테마 편집기 방식이에요. 칸 수십 개를 한 줄로 늘어놓으면 어디 문구인지 몰라요 |
| 가운데는 진짜 부스 화면을 실제 크기 창(1280 x 800, iframe `/photobooth/preview`)에 그려 줄여요 | 부스 화면은 vh 를 써서 어드민 안에 그리면 어드민 창 높이를 따라가요. 미리보기에서는 카메라를 열지 않고, 사진을 올리거나 인쇄하지 않아요 |

## 동심지키미 소개 (`app/(ko)/admin/company`, #250)

회사 소개의 걸어온 길, 수상 이력, 고마운 분들을 재배포 없이 고쳐요. 예전에는 코드에 적혀 있어 세 언어를 고치고 배포했고, 앱 크레딧과 웹 명단이 따로 있어 어긋났어요(3차 QA 참가자 5명이 앱에 빠졌어요).

### 값이 흐르는 길

```
어드민 저장 → Supabase company_records, credit_people, qa_attendance
  → lib/company/server.ts 가 300초 묶어 읽음(저장하면 바로 버림)
  → /team, /en/team, /ja/team, /team/members, /credits/embed(앱 크레딧)
```

- 사이트는 저장하면 다음 접속부터, 앱 크레딧은 CDN 때문에 최대 1분 뒤에 바뀌어요. 화면에는 "1분 안에"로 적어요
- 조회 오류는 삼키지 않아요. 재생성 중에 던지면 Next 가 직전 정상 페이지를 계속 내보내요(블로그 #188). 행사처럼 코드에 남은 값으로 돌리면 지운 줄이 되살아나요
- 빌드와 로컬 개발에서만 `lib/company/fallback.ts` 를 써요. 이력은 옮겨 올 때의 값, 명단은 빌드에서는 비움, 로컬에서는 지어낸 이름이에요
- 앱 크레딧은 명단만 못 읽으면 "도와준 분들" 칸을 빼고 열려요. 이 응답은 CDN 에 남기지 않아요

### 일정과 잇는 방법

행사는 일정 화면에서 만들고, 여기서는 그 일정을 소개 페이지에 올릴지 정해요. 같은 일을 두 곳에서 적지 않게요.

| 정한 것 | 이유 |
| --- | --- |
| 날짜가 지난 행사와 이름에 QA 가 든 테스트를 "올릴 일정"으로 띄우고 사람이 올려요 | 일정 이름은 내부용이에요("서울게임타운2 부스", "청춘대로 건국대 vs 세종대"). 자동으로 올리면 그대로 나가요 |
| 일정 표에 합치지 않고 표를 나눠요 | 일정은 이름 40자, 일 단위 날짜가 필수라 월까지만 아는 수상을 담지 못해요. 수상이 지표 차트에 섞이면 안 돼요 |
| 일정을 지워도 올린 이력은 남아요(`on delete set null`) | 달력 정리가 공개 이력을 지우면 안 돼요 |
| 건너뛴 일정은 다시 뜨지 않아요(`company_record_skips`) | 팀 내부 행사가 후보에 계속 남지 않게요 |
| 앞으로 있을 행사는 소개 페이지에 넣지 않아요 | 홈 팝업과 `/event` 가 이미 맡고 있어요 |

### 이력

| 정한 것 | 이유 |
| --- | --- |
| 날짜는 일까지, 월까지를 고르고 연월일은 목록에서 골라요. 월까지면 1일로 저장해요 | 2026.07 처럼 날을 모르는 수상이 있어요. 고르게 하면 없는 날짜와 형식 실수가 없어요(NN/g 슬립 예방). 앞으로 올 날짜는 막아요 |
| 순서는 저절로. 걸어온 길은 오래된 순, 수상은 최신순, 같은 날은 넣은 순서 | 끌어서 순서를 맞추는 일을 없애요 |
| 영어, 일본어가 비면 그 언어 페이지에서 그 줄만 빠져요. 목록에 "영어 없음"을 띄워요 | 번역 안 된 내용을 노출하지 않는다는 사이트 규칙(docs/i18n.md)과 같아요 |

| 숨기기와 지우기를 나눠요. 지우기만 확인창 | 잠깐 가리는 일과 되돌릴 수 없는 일은 달라요. 추가와 수정은 오른쪽에서 이미 결과를 봐서 확인창을 또 띄우지 않아요 |
| QA 제목은 회차 번호로 미리 채워요 | 세 언어 문장 틀이 같아 번역할 일이 없어요 |

### 고마운 분들

횟수는 숫자로 고치지 않고 `이전 참여 횟수 + 회차에 온 수`로 계산해요. 저장을 두 번 눌러도 +2 가 되지 않고, QA 한 번을 입력하면 걸어온 길과 명단, 앱 크레딧이 함께 바뀌어요. 1, 2차는 누가 왔는지 기록이 없어 이전 참여 횟수에 들어 있어요. 그래서 지난 회차를 올릴 때는 참가자를 비워 둬요.

| 정한 것 | 이유 |
| --- | --- |
| 이름은 띄어쓰기를 뺀 값으로 비교해요(`name_key`). 겹치면 저장을 막고 동명이인인지 물어요 | 같은 사람이 둘로 갈리지 않게요 |
| 붙여넣은 이름을 이미 있는 분, 새로운 분, 비슷한 이름으로 나눠 보여 줘요. 비슷한 이름은 사람이 골라요 | QA 끝나고 명단을 한 번에 넣어요. 세 글자 이상에서 한 글자만 다르면 물어요. 두 글자 이름은 한 글자만 달라도 다른 사람이라 묻지 않아요 |
| 참가자 고르기는 커스텀 체크박스(`components/admin/Checkbox.tsx`)예요. 줄 전체가 눌리고, 고른 줄은 바탕과 굵기가 바뀌고, 오른쪽 횟수가 바로 올라가요 | 브라우저 기본 모양은 OS 마다 달라요. 진짜 입력은 숨겨 둬서 키보드와 화면 읽기 프로그램은 그대로 돼요. 색만으로 상태를 전하지 않아요(WCAG 1.4.1) |
| GitHub 는 아이디만 저장하고, 2회가 되어야 서버가 페이지로 내보내요 | 미리 저장해도 1회인 분의 주소가 HTML 에 나가지 않아요. 인프라 제공자는 바로 보여요 |
| 앱 크레딧 색은 횟수로 계산해요(1회, 2회, 3회 이상, 인프라) | 앱에서 처음 정한 규칙 그대로예요. 맨 위 색은 후원용으로 비워 둬요 |

### 실명

명단은 코드와 마이그레이션에 적지 않아요. 코드에 남기면 본인이 빼 달라고 해서 지운 이름이 장애 때나 다시 실행할 때 되살아나요.

- "완전히 지우기"는 줄을 진짜로 지우고 참여 기록도 함께 지워요. 저장본을 남기는 행사 설정과 다르게 이전 값을 보관하지 않아요
- 고친 기록(`company_audit`)에는 누가, 언제, 몇 번 줄을 바꿨는지만 남겨요
- 예전에 코드에 있던 이름은 공개 저장소의 git 기록에 남아 있어요. 사이트에서 지워도 기록은 그대로라, 삭제 요청이 오면 필요할 때 따로 판단해요
- 삭제 요구를 받으면 10일 안에 결과를 알려야 해요(개인정보 보호법 시행령 제43조)

### 무엇을 어떻게 읽나 (`lib/release/`)

| 파일 | 하는 일 |
| --- | --- |
| `board.ts` | 순수 판단. 두 스토어 값을 스토어마다 고유한 단계, 누가, 지금 할 수 있는 일로 바꿔요. 테스트(`board.test.mjs`)는 11/8 실제 값과 상황별 값으로 |
| `stores.ts` | 스토어 읽기. App Store 는 출시용 키(App Manager)로 GET 만. Play 는 트랙 출시 목록을 읽고, 단계적 출시 비율과 승인된 앱 이름은 편집(edit) 안에서만 보여 편집을 열어 읽고 커밋하지 않고 지워요. 커밋하지 않은 편집은 스토어에 영향이 없어요 |
| `links.ts` | 콘솔 바로가기. Play 주소에는 계정 번호(`/u/1`) 대신 `authuser=팀 계정`을 붙여요. 아무것도 안 붙이면 첫 구글 계정(개인)으로 열려 "개발자 계정 만들기"가 떠요 |
| `server.ts` | 1분 캐시. "다시 읽기"는 캐시를 비워요(같은 서버에서 10초 안에 또 누르면 그대로) |

나라별 반영은 애플 공개 조회(iTunes lookup), 승인 안 된 Play 변경은 Play 스토어 페이지 제목(누구나 보는 값)과 견줘요. Play 는 나라별로 보이는 버전을 알려 주지 않아요.
최근 출시는 일정의 "iOS x.y.z 출시", "Android x.y.z 출시" 줄이에요(`docs/metrics-collection.md`).

Android 버전은 Play 출시 이름("400 (4.0.1)")의 괄호 안에서 읽어요. 이름 앞 번호가 실제 빌드와 다르면 이전 출시 이름이 남은 것이라 믿지 않고, 같은 빌드 번호로 나간 iOS 버전으로 불러요. 그것도 없으면 "빌드 400"으로 불러요(#292). 2026-11-09 에 빌드 400(4.0.1)이 Play Console 에서 "382 (3.2.7)" 이름으로 나가 어드민에 3.2.7 로 보였어요. 두 스토어가 같은 빌드 번호를 쓰는 걸 기대고 있어요.

실제 스토어 값을 그대로 찍어 보는 스크립트: `node --env-file=.env.local scripts/release-check.mjs` (읽기만 해요).
로컬 개발 서버에서는 스토어에 닿지 않고, 화면 위 "로컬 가짜 상황"으로 상황마다 바꿔 봐요(`lib/release/fixtures.ts`, 실제 판단 함수를 그대로 거쳐요).

## 출시 조작 (#231)

출시 화면의 "지금 할 수 있는 일" 상자에서 바로 눌러요. 콘솔 바로가기는 그대로 옆에 둬요.

| 스토어 | 할 수 있는 것 | 단계 |
| --- | --- | --- |
| App Store | 버전 칸 이름 바꾸기(빌드 안 버전과 맞추기), 빌드 붙이기, 제출 취소, 단계적 출시 멈춤과 이어 가기 | 1 |
| App Store | 심사에 내기, 지금 출시하기, 단계적 출시 바로 모두에게 | 2 |

관리형 게시의 "게시"와 반려 사유 보기는 API 가 없어 콘솔 바로가기로 둬요.

### Play 출시 목록 한도

심사 단계(심사 중, 승인, 반려)는 `tracks.releases.list` 에만 있는데, 이 호출에는 문서에 없는 짧은 한도가 있어요(2026-11-08, 403 `Listing releases quota exceeded`). 그래서 평소에는 부르지 않아요.

| 알고 싶은 것 | 읽는 곳 |
| --- | --- |
| 올라간 빌드(프로덕션, 내부 테스트), 단계적 출시 비율 | 편집(edit)의 트랙 |
| 사용자에게 실제로 나가 있는 빌드 | Reporting API `fetchReleaseFilterOptions` |
| 심사 단계 | 올라간 빌드가 나가 있는 빌드보다 새로울 때만 출시 목록, 5분에 한 번(`site_settings` 의 `play_release_lists` 에 저장해 모든 서버가 같이 봐요) |

막히면 10분 동안 모든 서버가 쉬어요. 심사 단계를 모르면 "심사 진행 중"으로 보여 주고, 화면 나머지는 그대로예요. 심사 중인 출시가 편집 트랙에 어떻게 보이는지는 아직 실제로 보지 못했어요. 첫 출시 때 콘솔과 대조해요.

### 운영진에게 보이는 말

화면에는 운영진이 알아야 할 것만 써요. 키 이름, SQL 파일, 오류 코드, `main`, `PR`, `CI`, 호출 한도는 보이지 않아요. 운영진이 고칠 수 없는 문제는 "개발 담당자에게 알려 주세요", 일시적인 문제는 "잠시 뒤 다시 확인해 주세요"로 쓰고, 자세한 내용은 서버 기록에 남겨요(`StoreError` 의 `detail`). 스토어가 조작을 거절한 사유는 고칠 수 있는 정보라 보여 줘요.

## 게임 화면은 늘 지금 상태로 (#182)

게임 상태는 앱에서 바뀌어요. 방장이 시작하면 진행 중, 판이 끝나면 다시 대기 중(FINISHED 로 남지 않아요), 방이 비면 사라져요. 어드민은 Relay 스토어를 세션 내내 하나로 써서, 한 번 읽은 목록을 다시 묻지 않으면 연 뒤에 시작한 방이 계속 "대기중"으로 보여요.

- 게임 목록(열린 방과 끝난 판 첫 쪽), 개요, 게임 상세는 30초마다 다시 읽어요. 화면을 보고 있을 때만 읽고, 다른 탭에 있다 돌아오면 바로 한 번 읽어요(`lib/admin/useLiveRefresh.ts`)
- `store-and-network` 로 읽어요. 보던 화면은 그대로 두고 뒤에서 받은 값으로 바꿔서 뼈대로 깜빡이지 않아요
- 끝난 판의 기록 상세는 바뀌지 않아서 다시 읽지 않아요

## 탈퇴한 참가자 (#186)

회원이 탈퇴하면 백엔드가 게임 기록에서 그 사람의 회원 번호를 지우고 닉네임을 "알수없음"으로 바꿔요(BE #223). 체포 수, MVP 같은 수치는 남아요.

- 기록 상세 참가자 표에서 `userId` 가 없으면 회원 화면 링크를 빼고 닉네임 옆에 "탈퇴" 표시를 붙여요. 갈 회원 화면이 없고, 원래 "알수없음"이라는 닉네임과 헷갈리지 않게 하려는 것이에요
- 로컬 목업은 세 판에 한 번 마지막 도둑을 탈퇴자로 만들어요(`lib/admin-mock/gameHistories.ts`)

## 무전 사용 시간과 동네 이름 (#315)

백엔드가 어드민 GraphQL 에 두 값을 더했어요. 경찰 무전 사용 시간(`radioSeconds`, BE #239)과 플레이 구역의 동네 이름(`placeName`, BE #241)이에요.

| 어디에 | 무엇을 |
| --- | --- |
| 게임 목록 | 방과 끝난 판 줄의 둘째 줄 맨 앞. 시도를 떼고 짧게("강남구 역삼동"), 마우스를 올리면 전체 |
| 방 상세, 끝난 판 상세 | 위치 카드 지도 위 첫 칩에 동네 이름 전체 |
| 끝난 판 상세 | 기록 카드의 경찰 줄마다 "무전 5분", 경찰 제목 줄에 합계. 이벤트 게임은 무전을 못 써서 빼요 |
| 유저 상세 | 계정 카드의 "무전 사용"(지금까지 쓴 시간) |

| 정한 것 | 이유 |
| --- | --- |
| 두 값은 본 쿼리와 나눠서 읽어요(`lib/admin/useOptionalQuery.ts`) | 운영 서버에 필드가 없으면 스키마 검사가 쿼리 전체를 거절해요. 나누면 백엔드가 나가기 전에도 화면은 그대로 열리고, 나간 뒤에는 다음으로 다시 읽을 때 값이 채워져요. 웹을 먼저 머지해도 돼요 |
| 배포 전이면 그 값만 안 그려요 | 줄마다 "서버 업데이트 뒤에"를 적으면 시끄러워요. 이름 칩, 무전 칸, 계정의 "무전 사용" 줄이 빠지기만 해요 |
| 무전 시간은 분까지만, 1분 넘으면 내림 | 백엔드가 2분마다 오는 토큰 재발급으로 세서 한 번 접속에 최대 2분 적게 나와요. 초까지 적으면 정확해 보여서 오히려 헷갈려요. 기록 카드 아래에 적어 뒀어요 |
| 합계는 줄마다 보이는 분을 더해요 | 초를 다 더해 내리면 줄(1분, 5분)과 합계(7분)가 어긋나 보여요 |
| 무전은 경찰 줄에만, 쓰지 않았으면 "무전 안 씀" | 무전은 경찰만 써요(도둑은 서버가 막아요) |
| 무전 줄은 값으로 짝을 지어요(`attachRadio`) | 참가자 줄에는 id 가 없어요. 순서에 기대지 않고 회원 번호, 팀, 나간 시각, 기록으로 맞추고, 같은 값이 둘이면(이벤트 게임 재입장, 탈퇴자 여럿) 몇 번째인지까지 봐요 |
| 동네 이름이 비면 8초 뒤 세 번까지 다시 물어요 | 백엔드는 처음 보는 곳을 한 번에 5곳까지, 3초까지만 찾고 나머지는 뒤에서 마저 찾아 저장해요. 목록은 30초마다 다시 읽어서 따로 묻지 않아요 |
| 이름이 없으면 그 자리를 비워요 | 구역을 아직 안 정한 대기 방이거나, 백엔드가 주소를 아직 못 찾았거나 찾지 못한 곳이에요(실패한 곳은 10분 뒤 다시 찾아요) |

알아 둘 것:

- 이름은 구역 가운데 기준이에요(원형은 중심, 다각형은 무게중심, 오목하면 구역 안 한 점). 구역이 동 경계에 걸치면 한쪽 동만 나와요
- 이름은 약 100m 단위로 저장돼서, 가까운 두 구역은 같은 이름이 나와요
- 무전 합계와 순위는 화면 없이 SQL 로 봐요(BE #239). 무료 플랜은 한 달 5,000분을 넘기면 그 달 무전이 막혀요
- 로컬 목업은 지난 게임 4번과 유저 4번이 배포 전처럼 답해요(`lib/admin-mock/handlers.ts`)

## 게임 상세 현장 운영 (#178)

부스에서 방을 열 때 하는 일 두 가지(이벤트 게임 켜기, 참가 QR 보여 주기)를 게임 상세 맨 위 카드 하나에 모았어요(`components/admin/games/`). 대기 중이거나 진행 중인 방에만 보여요. 끝난 방에는 할 일이 없어서 카드 자체를 빼요.

| 정한 것 | 이유 |
| --- | --- |
| 이벤트 게임은 스위치. 대기 중에는 누르는 즉시 바뀌고 묻지 않아요 | 스위치는 저장 버튼 없이 바로 적용될 때 쓰는 컨트롤이에요(NN/g 토글 가이드를 따르는 Mesa, Michelin 디자인 시스템). 대기 중에는 다시 누르면 되돌아가서 확인 창이 일만 늘려요 |
| 진행 중에 켤 때만 확인 창 | 진행 중에는 끌 수 없어서(BE #214) 되돌릴 수 없는 조작이에요. 확인 창은 되돌릴 수 없을 때만 띄워야 무시하고 누르는 습관이 안 생겨요 |
| 못 누르는 스위치는 바로 아래에 이유를 적어요 | 이유 없이 흐린 컨트롤은 사용자가 원인을 추측하게 해요(Smashing Magazine "Usability Pitfalls of Disabled Buttons"). 툴팁은 폰에서 안 보여서 글로 둬요 |
| 누르자마자 스위치가 움직이고, 실패하면 되돌린 뒤 빨간 글로 이유를 남겨요 | 낙관적 갱신. 실패는 토스트가 아니라 카드 안에 남겨요. 토스트는 2초 뒤 사라져 부스에서 놓치기 쉬워요 |
| 운영 서버에 기능이 없을 때를 따로 알려요 | 백엔드 #214 가 main 에 나가기 전에도 화면을 먼저 내보내려고요. 스키마 검사 오류(FieldUndefined)로 알아봐요(`lib/admin/notDeployed.ts`) |
| 15초마다 게임 상태를 다시 읽어요(화면을 볼 때만) | 앱에서 방장이 게임을 시작해도 화면은 몰라요. 들어올 수 있는지 안내가 상태에 달려 있어서 예전 상태로 두면 틀린 안내를 해요 |
| 참가 QR 은 버튼을 눌러야 열려요 | 상세 화면에 큰 QR 을 늘 띄우면 다른 정보를 밀어내요. 필요할 때만 여는 점진적 공개예요 |
| 지금 들어올 수 없으면 QR 옆에 노란 안내 | 일반 게임은 대기 중에만, 이벤트 게임은 진행 중에만 들어와요. 찍고 나서 실패하는 것보다 보여 주기 전에 아는 게 나아요 |
| QR 은 다크 모드에서도 흰 바탕, 검은 점, 둘레 여백 4칸 | 색을 뒤집거나 둘레가 어두우면 못 읽는 카메라 앱이 있어요(Tor Browser, GNOME Decoder 이슈). 둘레 여백 4칸은 QR 규격(ISO/IEC 18004)이에요 |
| 크게 띄우기: 흰 화면 가득 QR, 아래에 초대 코드 | 부스에서 노트북이나 폰을 그대로 내밀어요. 화면에서 찍을 땐 거리 10 : 크기 1 정도가 필요해서 짧은 쪽의 72% 까지 키워요. 초대 코드를 같이 적어 카메라가 안 되면 손으로 넣게 해요 |
| 크게 띄운 동안 화면 꺼짐 막기, 바탕을 눌러도 안 닫힘 | 방문객이 화면을 만지거나 잠깐 기다리는 사이 꺼지면 다시 깨워야 해요(Screen Wake Lock, 안 되는 브라우저는 그냥 둬요). 닫기 버튼과 Esc 로만 닫아요 |
| 유입 꼬리표는 행사 링크(#171) 중에서 고르기만 | 꼬리표를 손으로 지으면 같은 행사가 다른 이름으로 갈려요. 고른 링크의 출처, 매체, 캠페인을 그대로 쓰고 구분만 `join` 이라 링크 결과에 같이 잡혀요. 처음엔 가장 최근 링크, 그다음부턴 지난번에 고른 것 |
| 창 안 스크롤이 뒤로 넘어가지 않게 | 어드민 셸 뒤에 공개 사이트 문서가 깔려 있어서 폰에서 끌면 뒤가 움직여요. 창은 `overscroll-contain`, 크게 띄운 화면은 터치 스크롤을 막아요 |

## 스케일 주의 (백엔드 값 그대로 읽기)

- 팀 승률은 백엔드가 이미 0~100 퍼센트로 줘요. 프론트에서 또 ×100 하지 않아요.
- 평균 게임 시간은 백엔드 AVG라 소수가 와요. 표시 전에 정수 초로 반올림해요.

## 지표 화면 - 콘솔을 옮기지 않고 질문에 답하기 (#145)

인스타, GA4, App Store, AdMob 숫자를 한 화면에 모았지만 콘솔 화면을 그대로 옮기지는 않았어요. 질문 순서로 놓았어요.

- **탭 여섯** - 요약, 인스타그램, 유입 경로, 검색(#309), 스토어, 앱과 광고. 한 화면에 다 두니 노트북에서 대여섯 화면을 내려야 끝이 나왔어요. 매일 여는 사람은 요약만 보고, 맡은 일이 있는 사람은 그 탭으로 가요(GA4, App Store Connect 도 요약과 상세 보고서를 나눠요). 보고 있는 탭은 주소 `?tab=` 에 남아 링크로 공유하면 같은 탭이 열려요.
- **요약 맨 위 숫자 하나** - 이 기간 앱 첫 실행 횟수를 48px 로 크게, 이전 기간 대비 증감과 Android, iOS 추이를 옆에 둬요. 숫자를 늦게 받은 소스가 있으면 그 위에 경고 배너를 띄워요.
- **"모든 경로를 합친 흐름"과 "인스타그램에서 온 것"을 나눠요** - 처음엔 "인스타에서 게임까지"라는 제목 아래 인스타 숫자와 사이트 방문, 설치, 첫 실행을 한 줄로 이었는데, 뒤의 숫자는 검색, 행사 QR, 직접 입력까지 모든 경로를 더한 값이라 인스타에서 온 것처럼 읽혔어요. 인스타에서 왔다고 확인되는 건 사이트 방문과 다운로드 버튼 클릭까지라 거기서 끊고, 설치와 첫 실행은 경로를 가를 수 있게 되면(#144 배포, App Store 캠페인 리포트) 이어요. 단계마다 세는 대상이 달라 비율로 잇지 않는 건 그대로예요.
- **날마다** - 차트 순서는 위 격자와 같아요(인스타 → 웹 → 버튼 → App Store → 첫 실행 → 게임). 지표 여섯 개가 서로 다른 것을 세서, 지표를 바꿔 끼우는 큰 차트 하나(Plausible) 대신 같은 높이의 작은 차트를 나란히 뒀어요.
- **필터는 머리 오른쪽 한 줄** - 기간, 이전 기간 겹치기, CSV 만 둬요. 모든 숫자와 차트가 같은 기간을 따라요. 기간을 바꾸면 새 숫자가 올 때까지 이전 화면을 흐리게 둬요(뼈대로 바꾸면 깜빡이고 스크롤이 튀어요).
- **기간은 7일, 4주, 13주** - 28일, 91일이라 기간마다 요일 수가 같아요. 주말에 몰리는 숫자를 이전 기간과 공평하게 비교해요(Plausible, Search Console 도 28일을 기본으로 써요).
- **증감** - 화살표와 색을 같이 써요. 여기 숫자는 다 늘면 좋은 것이라 늘면 초록, 줄면 빨강 대신 회색이에요(Polaris). 비율은 이전 기간이 20 이상일 때만 붙여요. 이전 기간 중 그 소스를 모으기 전인 날이 있으면 증감을 숨기고 "이전 기간 숫자 없음"이라고 적어요(인스타는 9월 9일부터 있어서, 안 그러면 크게 늘어난 것처럼 보여요).
- **숫자 옆에 기준** - 화면 맨 아래에 소스마다 마지막으로 들어온 날을 적고, 미국 서부 날짜로 오는 인스타는 하루 뒤로 옮겨 한국 날짜에 맞췄다고 밝혀요.

### 탭마다 담은 것과 비율

마케터가 먼저 보는 건 개수보다 비율(효율)이에요. 비율 칸은 분자와 분모를 같이 적고(예: 14 / 369), 분모가 30 보다 작으면 "숫자가 적어 참고만 해요"를 붙이고 증감을 숨겨요. 비율의 증감은 %p 로 적어요.

| 탭 | 묶음 |
| --- | --- |
| 요약 | 앱 첫 실행 큰 숫자, 모든 경로를 합친 흐름(사이트 방문, 스토어로 이동, App Store 최초 다운로드, 앱 첫 실행, 진행된 게임), 신규 사용자 퍼널(첫 실행, 로그인, 방 입장, 게임 플레이, 다음 주에도 플레이, 플랫폼과 나라 고르기, #157), 핵심 비율(사이트 전환율, 활성화율, 다음 날 다시 온 비율, Android 삭제 비율), 인스타그램에서 온 것, 일정 |
| 인스타그램 | 조회수, 프로필 방문, 링크 클릭, 팔로워, 프로필 방문률, 링크 클릭률, 게시물 표(조회수, 도달, 참여율, 공유로 정렬) |
| 유입 경로 | 사이트 방문, 스토어로 이동(다운로드 링크와 사이트 버튼으로 나눔), 사이트 전환율, 채널별 표, 소스별 표 |
| 검색 | 페이지 보기(답 한 문장, 사이트 페이지 × 언어 표, 블로그 글과 모집글 표, 누르면 상세)와 검색 실적 보기(숫자 한 줄, 날마다, 검색어). 흐름과 근거는 `docs/search-indexing.md` |
| 스토어 | 전체 / App Store / Google Play 를 골라요(#147). 전체: 최초 설치(합, 스토어별, 나라별), 스토어 화면에서 설치까지 나란히. App Store: 노출, 제품 페이지 조회, 조회율, 최초 다운로드, 전환율, 나라별 표, 어떻게 받았나(검색, 웹 링크, 다른 앱 링크와 추이), 받고 7일 안에 지운 비율(#160). Google Play: 스토어 방문자, 획득, 전환율, 최초 설치, 나라별, 남아 있는 설치(설치된 기기, 삭제), 안정성과 평점 |
| 앱과 광고 | 첫 실행(앱 첫 실행, 스토어 최초 설치), 사용(하루 활성 사용자, 진행된 게임, 판당 인원, 게임 참가), 남는 사람(활성화율, 1일과 7일 뒤 다시 온 비율, 삭제 비율, 푸시 열람률), 광고(게재율, eCPM, ARPDAU, 게임 1회당 광고 노출) |

- 좋아진 쪽은 초록, 나빠진 쪽은 회색이에요. 삭제 비율처럼 줄어야 좋은 비율은 거꾸로 칠해요. 삭제, 비정상 종료 같은 개수도 같아요.
- **Google Play 는 늦게 들어와요(#147).** 구글이 3~7일 늦게 채워서 기간 끝까지 없는 날이 많아요. 그대로 비교하면 늘 줄어든 것처럼 보여서, 들어온 날까지만 세고 비교 기간도 같은 날 수로 잘라요. 칸 아래에 "9월 30일까지, 이전 기간도 같은 24일"처럼 적어요. 이 지연은 늘 있는 일이라 맨 위 "덜 들어온 숫자" 경고에는 넣지 않았어요.
- **요약 흐름의 설치는 두 스토어 합이에요.** 예전엔 App Store 최초 다운로드만 있어서 Android 설치가 흐름에서 빠져 있었어요. 칸 아래에 스토어별 숫자를 적어요.
- **스토어는 탭 하나로 모으고, 그 안에서 스토어를 골라요.** 처음엔 스토어 숫자를 유입 경로(스토어 화면)와 앱과 광고(설치, 남아 있는 설치, 안정성)에 나눠 뒀는데, 스토어 화면을 고치는 사람은 한 스토어를 콘솔 순서대로 끝까지 봐야 해요. 화면 전체에 스토어 고르기를 두지 않은 건 인스타, 사이트, 퍼널 숫자가 스토어로 나뉘지 않아서예요. 고른 스토어는 주소 `?store=appstore|play` 에 남아요. 전체 보기는 두 스토어 숫자를 더하지 않고 나란히 둬요. 고르는 말은 퍼널 카드의 "전체 / iOS / Android" 와 맞췄어요("두 스토어"는 버튼 이름보다 설명처럼 읽혀서 바꿨어요). App Store 노출은 이미 깐 사람도 세고 Google Play 방문자는 앱이 없는 사람만 세서, 더하면 뜻이 없는 숫자가 돼요. 더하는 건 최초 설치와 나라별 설치뿐이에요.
- **스토어 화면 숫자를 따로 보는 이유.** App Store 노출은 대부분 스토어 검색 결과에서 나와요(10/3~10/5 607회 중 596회). 사이트를 거친 숫자만으로는 "스토어에서 보고도 안 깐" 단계가 안 보였어요. 나라별 표는 노출 1,000회당 다운로드로 견줘요. 일본처럼 노출은 많은데 설치가 적은 나라를 찾으려는 표예요.
- **어떻게 받았나(App Store, #160).** 행사가 있던 9월은 웹 링크(QR, 사이트)로 받은 게 검색과 같고(34, 34), 행사가 없던 8월은 33건 중 28건이 검색이었어요. 행사가 설치를 얼마나 끌었는지 보이는 숫자라 네 칸과 추이 차트로 둬요. 출처 앱 이름(카카오톡 등)은 칸이 잘게 나뉘어 최초 다운로드로는 거의 안 남아서 화면에 넣지 않았어요.
- **받고 금방 지운 사람(iOS).** Android 는 Play 의 삭제가 있는데 iOS 는 없었어요. 애플 설치와 삭제 리포트는 분석 공유에 동의한 사람만 세서 개수 대신 7일 안에 지운 비율만 보여요. 받은 지 7일이 안 지난 날은 빼고, 센 기간을 옆 칸에 적어요.
- **남아 있는 설치(Android).** 우리 게임은 사람이 모일 때 켜는 앱이라 하루 활성 사용자는 늘 작아요. 대신 "행사 때 깐 사람이 아직 폰에 두고 있나"를 봐요. Google Play 의 활성 기기(깔려 있고 30일 안에 켜진 기기)를 기간 첫날 전날과 마지막 날로 견주고, 추이 차트에 행사 마름모를 겹쳐요.
- **안정성.** 행사 1주일 전 앱 변경 마감처럼 행사 날 앱이 멈추지 않게 하는 게 중요해서, 비정상 종료를 빌드별로 적어요. 버전 이름은 파일에 없어 빌드 번호(버전 코드)로 적어요.
- 이 기간 전체가 그 소스를 모으기 전이면 0 이 아니라 "-" 와 "이 기간엔 숫자가 없어요"를 보여요.
- 일정은 어드민 "일정" 화면에서 성격(행사, 홍보, 테스트, 기타)을 골라 넣고, 지표의 모든 차트에 마름모로 겹쳐요. 인스타 게시물은 동그라미예요. 게시물과 일정은 모양으로, 일정의 성격은 마름모 색과 이름으로 갈라요(#165, `docs/metrics-events.md`). 앱 출시(iOS, Android)는 매일 지금 배포 중인 버전을 보고 자동으로 들어오고 목록에 "자동"이 붙어요. 날짜는 App Store Connect 의 "배포 준비됨", Play Console 의 "출시일"과 같은 날이에요.
- **일정 달력**(`EventsCalendar`) - 어드민 "일정" 화면(`/admin/schedule`, #302). 예전엔 지표 요약 탭 맨 아래였어요. 날짜를 누르면 아래에 그날 일정과 입력 칸이 열려서 날짜를 따로 고를 필요가 없어요. 행사는 진한 칩, iOS 업데이트는 회색 점과 글씨예요. "iOS 업데이트 보기"로 끄면 행사만 남아요. 날짜를 고르지 않았을 때는 이 달의 행사를 위에, 업데이트는 접어서 아래에 둬요. 앞으로 있을 행사도 1년 뒤까지 넣을 수 있어요. 폰에서는 칸에 이름 대신 점만 찍어요. 분석 도구들(GA4, Amplitude)은 일정을 목록으로 다루지만, 우리는 행사 단위로 움직여서 날짜 간격이 보이는 달력이 더 맞아요.
- **이 기간 일정**(`ScheduleList`) - 요약 탭 맨 아래. 지금 보는 기간의 일정을 날짜마다 한 줄로 읽기만 해요. 줄을 누르면 일정 화면에서 그날이 열리고, 지난 날은 "7일 비교"로 그날부터 7일을 그 전 7일과 견줘요. 앱 업데이트는 접어 둬요.
- **툴팁**(`components/admin/Tooltip.tsx`) - 브라우저 기본 툴팁(title)은 늦게 뜨고 작고 다크 모드를 안 따르며, 키보드와 터치로는 안 떠서 쓰지 않아요. 마우스는 올리면, 키보드는 초점이 오면, 터치는 누르면 열려요. 표의 가로 스크롤 상자에 잘리지 않게 화면 위에 띄워요.
- 게시물 표에서 줄을 누르면 오른쪽(폰은 아래)에서 그 게시물의 상세가 열려요(`PostDrawer`). 하루에 늘어난 조회수, 도달, 공유, 프로필 방문을 골라 보고, 올린 뒤 3일 안에 붙은 몫과 누적 숫자를 보여요. 인스타그램은 게시물의 날짜별 숫자를 주지 않아 매일 아침 찍는 누적값의 차이로 그려서, 기록을 시작한 2026-10-06 전은 비어 있어요.

### 비교 기간 고르기 (`components/admin/metrics/CompareMenu.tsx`, #152)

예전 "이전 기간 겹치기" 버튼 자리에 "비교: 이전 기간 ▾" 메뉴를 뒀어요. 마케터가 가장 자주 하는 질문이 "행사(광고) 주간이 평소보다 어땠나"라서, 바로 앞 기간 말고 떨어진 기간과도 비교할 수 있게 했어요.

| 고를 것 | 왜 이렇게 | 일부러 안 한 것 |
| --- | --- | --- |
| 이전 기간(기본) | 바로 앞 같은 길이 | |
| 요일 맞춘 이전 기간 | 7일 단위가 아닌 기간은 같은 요일부터 시작하게 7의 배수만큼 앞으로 옮겨요(GA4 "요일 일치"와 같아요) | 7일 단위 기간에서는 이전 기간과 같아서 목록에서 빼요 |
| 직접 고르기 | 시작일만 누르면 지금 기간과 같은 길이가 칠해져요. 길이가 다르면 합계 비교가 불공평하고 차트를 날짜별로 겹칠 수 없어요 | 길이가 다른 비교, 지금 기간과 겹치는 비교(같은 날을 두 번 셈) |
| 비교 안 함 | 증감, 회색 선, "이전 기간 N" 줄을 모두 숨겨요 | |

- 작년 같은 기간은 데이터가 2026-04 부터라 내년까지 비어 있어서 넣지 않았어요.
- 항목마다 실제 날짜를 같이 적어, 고르기 전에 무엇과 비교하게 되는지 보여요. 탭 아래에도 "지금 9월 19일~9월 25일, 비교 기간 9월 1일~9월 7일"을 늘 적어요. 직접 고른 비교는 화면 문구가 "이전 기간"이 아니라 "비교 기간"이 돼요.
- 차트 툴팁의 회색 선 값에는 "비교 기간 9.1"처럼 그날이 언제인지 같이 적어요.
- 기간을 바꾸면 직접 고른 비교는 풀려요(새 기간과 겹치거나 길이가 달라지니까요).
- 일정 달력에서 일정이 있는 지난 날을 누르면 "이날부터 7일을 그 전 7일과 비교"로 바로 넘어가요. 행사를 적어 두는 이유가 "그 뒤 숫자가 어땠나"를 보려는 것이라, 기간과 비교를 따로 맞추지 않아도 되게 했어요.
- 비교 상태는 주소(`?cmp=dow|off|2026-09-01`)에 남아 링크로 공유돼요.

### 기간 직접 고르기 (`components/admin/metrics/DateRangePicker.tsx`)

기간 버튼(7일, 4주, 13주)은 그대로 두고 옆에 "직접 선택"을 하나 더 뒀어요. 매일 여는 사람은 버튼 한 번으로 끝나고, "축제 5일 동안 어땠나"처럼 특정 기간이 궁금할 때만 열어요(GA4, Plausible 과 같은 배치).

| 정한 것 | 이유 |
| --- | --- |
| 왼쪽에 자주 쓰는 기간을 줄로(어제, 지난 7일, 14일, 4주, 13주, 이번 달, 지난달, 모은 날 전체) | "지난달"을 찾으려고 달력을 넘기게 하지 않아요 |
| 넓은 화면은 두 달, 폰은 한 달. 폰에서는 화면 가운데 뜨고 뒤를 어둡게 덮어요 | 기간이 달을 넘는 일이 많아요. 폰은 폭이 모자라요 |
| 시작일을 누르고 끝날 위에 올리면 기간이 미리 칠해져요 | 누르기 전에 어디까지인지 보여요 |
| 고르는 순간 바뀌지 않고 "적용"을 눌러야 다시 불러와요 | 고르다 마음이 바뀌어도 뒤의 화면이 흔들리지 않아요 |
| 아래에 고른 기간, 며칠인지, 무엇과 비교하는지 적어요. 7일 단위가 아니면 두 기간의 요일 수가 다르다고 알려요 | 5일을 고르면 그 앞 5일과 비교하는데, 주말이 들어간 수가 다를 수 있어요 |
| 고를 수 있는 날은 2026년 4월 1일(수집 시작)부터 어제까지, 한 번에 366일까지 | 오늘은 숫자가 아직 다 안 들어왔어요. 서버(`/api/admin/metrics?from=&to=`)도 같은 규칙으로 막아요 |
| 키보드: 화살표 하루, 위아래 한 주, PageUp/PageDown 한 달, Home/End 주의 처음과 끝, Enter 고르기, Esc 닫기 | 마우스 없이도 골라요 |
| 고른 기간은 주소(`?from=2026-09-23&to=2026-09-27`)에 남아요 | 링크를 보내면 같은 기간이 열려요 |
| 주는 일요일부터 | 국내 달력이 대부분 일요일부터예요 |

날짜 계산은 `lib/metrics/dashboard/calendar.ts` 에 따로 두고 테스트했어요(`calendar.test.mjs`).

### 차트 색

`app/globals.css` 의 `--chart-1`, `--chart-2`, `--chart-prev`, `--chart-up` 을 써요. 상태색(`--sd-warning` 등)은 좋다, 나쁘다를 뜻할 때만 쓰고 선 색으로 쓰지 않아요.

| 토큰 | 라이트 | 다크 | 확인한 것 |
| --- | --- | --- | --- |
| `--chart-1` | `#3f63d9` (경찰 파랑) | `#22b047` | 바탕 대비 3:1 이상 |
| `--chart-2` | `#eb6834` | `#9085e9` | 첫 선과 적록색약, 청황색약 시뮬레이션에서도 갈림(색 차이 22 이상, 기준 8) |
| `--chart-prev` | `#b0b3ba` | `#5b5f66` | 일부러 옅게. 값은 툴팁과 숫자 칸에 있어요 |
| `--chart-up` | `#0a7d63` | `#26c199` | 작은 글자 대비 4.5:1 이상 |

다크 액센트 네온 초록(`#38f55b`)을 선으로 쓰지 않는 이유: 밝기가 너무 높아(OKLCH L 0.85, 다크 차트 권장 0.48~0.67) 어두운 바탕에서 눈이 부시고, 예전 둘째 선(노랑)과 나란히 두면 적록색약에게 색 차이가 4.1 로 같은 색처럼 보였어요. 두 진영 색은 그대로 두고 밝기만 낮춘 초록을 썼어요.
- **모바일 탭바** - 지표가 들어가 탭이 9개(375px 화면에서 한 칸 약 42px)가 됐어요. 이름이 모두 두세 글자(11px)라 아직 한 칸에 들어가서 그대로 두고, 더 늘면 묶을게요. 앱 설정은 탭에 넣지 않고 상단 헤더 아이콘으로 들어가요.
- "덕분에 늘었다"는 문장은 쓰지 않아요. 센 숫자만 보여 줘요.

## 스토어 페이지

App Store 와 Google Play 의 문구를 세 언어(한국어, 영어, 일본어)로 고쳐 보고, 만들 이미지의 규격을 찾는 곳이에요. 쓰는 사람은 마케터와 디자이너예요. 지금은 초안까지만 저장하고 스토어에는 아무것도 보내지 않아요.

### 콘솔의 불편함과 이 화면이 하는 일

| 콘솔에서 불편한 점 | 이 화면 |

| 긴 문구(60자 넘거나 여러 줄)는 전과 후를 따로 두지 않고 한 문장 안에서 지운 단어와 넣은 단어만 칠해요(`diffWords`) | 스토어 설명처럼 긴 글에서 한 단어를 바꾸면 두 덩어리를 눈으로 대조해야 했어요. 너무 길면(단어 수의 곱 25만 넘게) 전과 후를 통째로 보여요 |
| 목록은 더한 것(+)과 뺀 것(−) 칩, 순서만 바꿨으면 그렇게 적어요. 그림은 전후 작은 그림, 스크린샷 목록은 더하고 뺀 그림 | 목록을 글 둘로 비교하면 무엇이 빠졌는지 사람이 찾아야 해요 |
| "사용자에게 닿아요" 표시와 그것만 보기 | 점검, 최소 버전, 광고 끄기, 부스 닫기, 온라인 게임 입구, 출시 비율, 스토어로 보내기. 문제가 생겼을 때 먼저 볼 것만 추려요 |
| 화면, 사람, 기간(7일, 30일, 90일) 거르기를 주소에 남겨요(`?days=`, `?area=`, `?who=`, `?impact=1`) | "이날 이거 바뀐 거 봐 주세요"를 링크로 보내요 |
| 로그인 이력은 넣지 않았어요 | 물어볼 질문은 누가 무엇을 바꿨나예요. 로그인은 백엔드에서 일어나 웹이 정확히 남기기 어렵고, 마지막으로 들어온 때는 운영진 화면에 있어요. 외부 사람에게 어드민을 열 때 백엔드에서 남겨요 |

### 기록이 오는 곳

| 화면 | 어디서 | 남는 것 |
| --- | --- | --- |
| 앱 설정, 온라인 게임, 홈 미니게임, 일정, 그림 보관함, 스토어 페이지 초안(문구, 그림), 리뷰 답변 문구, 운영진 역할 | 공통 표 `admin_changes`(0028). 저장이 끝난 뒤 라우트가 `recordChange` 로 남겨요 | 전후 값 |
| 행사 | 이미 있던 저장본 `event_settings_history`. 판마다 바로 앞 판과 비교해요(첫 판은 일정에서 만든 기본값과) | 전후 값 |
| 출시 조작, 스토어로 보내기 | 이미 있던 `release_actions` | 한 일과 결과(끝남, 실패와 사유) |
| 동심지키미 소개 | 이미 있던 `company_audit` | 한 일만(값은 남지 않아요) |

- 이미 따로 남던 기록은 공통 표에 다시 쓰지 않고 화면이 같이 읽어요. 같은 일이 두 번 보이지 않게요.
- 기록을 못 남겨도 저장은 막지 않아요. 저장은 이미 끝났고, 0028 전에도 어드민이 멈추면 안 돼요. 한 출처를 못 읽으면 나머지만 보이고 위에 알려요.
- 입력하는 동안 저절로 저장되는 칸(스토어 페이지 초안)은 같은 사람이 같은 칸을 10분 안에 다시 고치면 한 줄로 합쳐요. "전"은 처음 것, "후"는 마지막 것이고, 결국 같아지면 줄을 지워요(`lib/changes/merge.ts`).
- 바꾼 사람 이름은 화면이 보낸 값을 믿지 않고 토큰의 번호로 백엔드에 물어요(`actorName`).
- 0028 이전 일은 행사, 출시, 동심지키미 소개만 보여요. 나머지 화면은 0028 을 실행한 뒤부터 쌓여요.

## 운영진 (`app/(ko)/admin/team`, #282)

누가 어떤 일을 맡는지 적어 두고, 다음 단계에서 역할에 맞는 지표를 개요에 먼저 보여 주려고 만들었어요.

### 역할

| 역할 | 하는 일 |
| --- | --- |
| 개발 | 출시, 안정성, 버그 |
| 디자인 | 프레임, 스토어 이미지 |
| 마케팅 | 유입, 스토어, 인스타 |
| 운영 | 행사, 신고, 고객 응대 |

### 화면에서 정한 것

| 정한 것 | 이유 |
| --- | --- |
| 처음 들어오면 맡은 일을 고르는 화면이 떠요. 여러 개 고르고, 나중에 고를 수도 있어요 | 한 사람이 여러 일을 맡아요. 고르기 싫은 사람을 막으면 안 돼요 |
| 고르거나 건너뛰면 다시 뜨지 않아요. 운영진 화면에서 언제든 바꿔요 | 매번 물으면 귀찮아요 |
| 역할은 볼 수 있는 화면을 줄이지 않아요 | 작은 팀이라 서로의 일을 자주 대신해요 |
| 자기 역할은 누구나, 남의 역할과 역할 목록은 운영 역할을 맡은 분이 고쳐요 | 남이 내 역할을 몰래 바꾸지 않게 해요 |
| 운영 역할을 맡은 분이 아직 없으면 누구나 고쳐요 | 처음 맡을 사람을 정할 수 있어야 해요 |
| 처음부터 있는 네 역할은 그림이 따로 있고 지울 수 없어요. 새 역할은 Lucide 아이콘 64개 중에 골라요. 소통, 사람, 만들기, 개발, 숫자와 돈, 운영과 행사, 안전과 문서, 그 밖에로 묶었어요 | 고르는 화면의 얼굴이라 그림을 맞췄어요. 어떤 일을 맡든 어울리는 아이콘이 있어야 하고, 묶어 두면 많아도 찾기 쉬워요. 아이콘을 손으로 그리지 않아요 |
| 역할을 고칠 때 처음 고르는 화면에서 어떻게 보이는지 같이 보여 줘요 | 이름이 길거나 설명이 비면 바로 보여요 |
| 다른 분이 먼저 고쳤으면 덮어쓰지 않아요 | 둘이 동시에 고쳐도 한쪽이 사라지지 않아요 |

### 값이 흐르는 길

- 구성원은 어드민에 들어온 사람이 저절로 쌓여요. `GET /api/admin/team` 이 토큰의 사용자 번호로 남겨요. 화면이 보낸 번호는 믿지 않아요
- 이름은 백엔드 어드민 정보에서 다시 읽어요(`actorName`)
- 저장은 운영 배포에서만 해요. 로컬은 가짜 값을 브라우저에 두고, 지우면 첫 화면을 다시 볼 수 있어요(`mock_admin_team`)

### 처음 연결하기

`supabase/migrations/0024_admin_team.sql` 을 Supabase SQL Editor 에서 한 번 실행해요. 네 역할이 같이 들어가요.

## 개요 카드 (`lib/admin/overview/cards.ts`, #284)

역할은 카드 키만 들고 있고(`admin_roles.cards`), 카드가 무엇을 어디서 읽는지는 카드 목록이 정본이에요. 새 기능에 카드를 붙이려면 목록에 하나 더하고 그림을 정하면 돼요.

### 화면에서 정한 것

| 정한 것 | 이유 |
| --- | --- |
| 공통 띠는 모두에게 같고 뺄 수 없어요 | 지금 게임이 돌고 있는지, 사람이 들어오는지는 누구나 먼저 봐요 |
| 역할을 여러 개 맡으면 역할마다 한 장씩 번갈아 넣어 8칸까지 채워요 | 앞 역할 카드만으로 칸이 차면 뒤 역할이 안 보여요 |
| 역할을 고르지 않았으면 팀 기본 카드(새 사용자, 미처리 버그, 미처리 신고, 다음 행사 준비)를 보여 줘요 | 빈 개요를 보여 주지 않아요 |
| 지표마다 모양이 달라요. 추이는 7일 꺾은선과 그 앞 7일 점선, 비율은 고리, 구글 기준이 있는 값은 기준선 막대, 쌓이는 일은 큰 숫자 | 숫자만 늘어놓으면 좋은지 나쁜지 읽어야 알아요 |
| 카드마다 기준 시점(실시간, 어제까지 7일, 최근 28일)을 적어요. 좁은 화면에서는 제목이 먼저라 숨겨요 | 실시간 게임 수와 어제까지 지표가 나란히 있어요 |
| 비율은 분모가 30보다 적으면 흐리게 두고 참고만 하라고 적어요 | 몇 명으로 낸 비율은 크게 흔들려요 |
| 쌓이는 일은 있으면 빨강, 없으면 파랑으로 다 끝났다고 말해요 | "색으로 상태를 말하기"와 같아요 |
| 넓은 화면은 한 줄 네 칸, 좁으면 두 칸. 줄마다 빈칸 없이 가장 작은 카드부터 넓혀요 | 빈칸이 있으면 카드가 빠진 것처럼 보여요 |
| 카드를 누르면 그 기능 화면으로 가요 | 개요는 출발점이고 일은 각 화면에서 해요 |

### 값이 흐르는 길

- 지표, 안정성, 출시, 점검 기한, 행사, 스토어 초안은 `GET /api/admin/overview?cards=` 가 화면에 놓인 카드만 계산해요. 카드 하나를 못 읽어도 나머지는 보여요
- 지표 표는 새벽과 아침에 쌓여서 1시간 같은 값을 써요. 지표 화면 API 와 달리 백엔드 게임 기록은 읽지 않아요
- 추이 카드는 소스마다 들어온 마지막 날을 끝으로 7일을 잡아요. App Store 페이지 조회는 애플이 며칠 늦게 줘서 끝 날짜가 더 앞이에요
- 게임 수, 승률, 종료 사유, 최근 게임, 처리 대기 건수는 화면이 백엔드에서 바로 읽어요(30초마다 새로)
- 이번 주 게임은 백엔드 숫자라 운영진이 한 판도 들어 있어요. 운영진을 뺀 수는 지표 화면에서 봐요
- 로컬에서 개요를 가짜 값으로 보려면 `.env.development.local` 에 `NEXT_PUBLIC_USE_DEV_GRAPHQL=false` 를 둬요. 3000 이 아닌 포트는 개발 서버가 막아요

## 역할과 카드 (`components/admin/team/RoleSheet.tsx`, #286)

운영진 > 역할에서 역할을 만들거나 고칠 때 그 역할의 개요 기본 카드를 골라요. 운영 역할을 맡은 분만 열 수 있어요.

### 화면에서 정한 것

| 정한 것 | 이유 |
| --- | --- |
| 두 단계로 나눠요. 1 이름과 아이콘, 2 보여 줄 카드 | 한 화면에 다 넣으면 처음 쓰는 사람이 무엇부터 할지 몰라요 |
| 카드는 이름이 아니라 실제 모양을 작게 줄여 보여 줘요. 숫자는 예시예요 | 이름만으로는 무엇이 보이는지 알기 어려워요 |
| 고르는 즉시 오른쪽 "이 역할의 개요"에 실제 배치 그대로 놓여요 | 고르는 일과 결과를 따로 오가지 않아요 |
| 넓은 화면은 갤러리와 미리보기를 따로 스크롤해요 | 아래 카드를 고르는 동안에도 미리보기가 보여요 |
| 8칸 막대와 "N칸 남았어요"를 보여 주고, 넘치면 넣기 전에 알려 줘요 | 자리가 왜 안 들어가는지 바로 알아요 |
| "비슷한 역할에서 시작하기"로 다른 역할의 카드를 채운 뒤 고쳐요 | 빈 칸을 처음부터 채우는 것보다 고치는 게 쉬워요 |
| 이름 검색과 성장, 게임, 안정성, 운영, 준비 묶음으로 찾아요 | 카드가 23장이라 훑기만으로는 길어요 |
| 미리보기에서 끌어서 순서를 바꾸고, 비켜 가는 카드는 미끄러지듯 움직여요 | 자리가 바뀌는 게 눈에 보여야 놓을 곳을 알아요 |
| 끌 때는 미끄러지는 카드가 아니라 격자의 고정된 칸 위치로 재요 | 움직이는 카드로 재면 같은 두 장이 앞뒤로 흔들려요 |
| 키보드로도 옮겨요. 화살표로 옮기고 Delete 로 빼요 | 마우스 없이도 쓸 수 있어야 해요 |
| 줄인 미리보기의 빼기 단추는 줄이지 않아요(28px) | 줄이면 12px 이 돼서 누르기 어려워요 |
| 갤러리와 미리보기는 `components/admin/overview/CardPicker.tsx` 하나로 내 개요 구성과 같이 써요 | 고치는 법이 한 가지예요 |
| 고친 채로 닫으면 버릴지 물어봐요 | 실수로 Esc 를 눌러도 고친 게 사라지지 않아요 |

### 값이 흐르는 길

- 고른 카드는 `admin_roles.cards` 에 저장해요. 서버가 아는 카드인지, 한 번씩인지, 8칸 안인지 다시 검사해요(`cardsProblem`)
- 저장하면 그 역할을 맡은 분들의 개요가 다음에 열 때 새 카드로 보여요
- 처음부터 있는 역할도 카드를 고칠 수 있어요. 그림만 그대로예요

## 지금 할 일 (`lib/admin/overview/tasks.ts`, #288)

따로 입력하는 할 일 목록이 아니라, 이미 있는 기능에서 처리를 기다리는 것만 모아요. 처리하면 저절로 사라져요.

| 일 | 언제 뜨나 | 무게 |
| --- | --- | --- |
| 미처리 신고 | 한 건이라도 있으면 | 급해요 |
| 미처리 버그, 답글 대기 리뷰 | 한 건이라도 있으면 | 챙겨요 |
| 출시 | 우리 차례이면 챙겨요, 막혔으면 급해요 | |
| 스토어 점검 기한 | 30일 안이면 챙겨요, 7일 안이거나 지났으면 급해요 | |
| 다음 행사 준비, 프레임 | 14일 안의 행사에 남은 준비가 있거나 기본 프레임이면 챙겨요, 3일 안이면 급해요 | |
| 보내지 않은 스토어 초안 | 한 칸이라도 있으면 | 참고 |

### 화면에서 정한 것

| 정한 것 | 이유 |
| --- | --- |
| 공통 띠 바로 아래, 내 지표 위에 둬요 | 숫자를 보기 전에 할 일을 먼저 봐요 |
| 급한 일부터 둬요. 빨강은 급해요, 노랑은 챙겨요, 파랑은 참고 | 색만 봐도 무엇부터 할지 알아요 |
| 내 역할의 카드와 이어졌거나 내 역할이 챙기는 일을 위에, 나머지는 "다른 역할의 일 N개"로 접어요 | 다 숨기면 아무도 안 챙기는 일이 생겨요 |
| 일마다 먼저 챙길 역할을 정해 뒀어요(`TASK_ROLES`). 신고는 운영, 리뷰는 운영과 마케팅처럼 | 카드에 없는 일도 주인이 있어야 해요 |
| 역할이 없으면 모든 일을 보여 줘요 | 접어 둘 기준이 없어요 |
| 누르면 그 기능 화면으로 가요 | 할 일은 각 화면에서 해요 |
| 예전 "처리를 기다리는 신고, 버그" 빨간 알림은 뺐어요 | 지금 할 일과 같은 내용을 두 번 보여 줬어요 |

할 일에 필요한 값(출시, 점검 기한, 행사, 초안)은 화면에 그 카드가 없어도 개요 요약 API 에서 같이 읽어요.
