# 인스타 리포트 (개발자용)

인스타 성과를 매일 모아 디스코드로 게시물 리포트와 급상승 알림을 보내는 장치 (#140).

## 왜 매일 모으나

인스타 API는 게시물 숫자를 "지금까지 누적"으로만 준다. 하루 단위 변화는 매일 찍어 둔
누적값의 차이로만 알 수 있어서, 찍지 않은 날은 나중에 되살릴 수 없다.
계정 전체 하루 지표도 최근 30일까지만 물을 수 있다.

## 데이터 흐름

```
GitHub Actions (instagram-report.yml, 매일 UTC 0시 = 한국 오전 9시)
  → POST /api/metrics/instagram (METRICS_CRON_SECRET)
  → lib/metrics/instagram/run.ts
      1. 토큰 준비 (metrics_tokens, 일주일마다 연장)
      2. 게시물 목록과 게시물마다 누적값 → instagram_media, instagram_media_daily
      3. 계정 하루 지표 → instagram_account_daily (처음 28일치, 이후 최근 며칠 다시)
      4. 게시물 리포트, 급상승 알림 → 디스코드 웹후크 (metrics_notifications 로 중복 방지)
```

블로그 동기화(`blog-sync.yml` → `/api/blog/sync`)와 같은 구조다. 서비스 서버와 DB를 건드리지
않는다.

| 파일 | 하는 일 |
| --- | --- |
| `lib/metrics/instagram/api.ts` | 인스타 Graph API 호출 |
| `lib/metrics/instagram/store.ts` | Supabase 읽기, 쓰기 |
| `lib/metrics/instagram/rules.ts` | 무엇을 언제 보낼지 (순수 함수, 테스트 있음) |
| `lib/metrics/instagram/messages.ts` | 디스코드 문구 (순수 함수, 테스트 있음) |
| `lib/metrics/instagram/run.ts` | 위를 순서대로 한 번 돌린다 |
| `lib/metrics/discord.ts` | 웹후크 전송 |
| `scripts/instagram-report.mjs` | 손으로 한 번 돌리기 |

`lib/metrics/` 아래 파일은 서로를 **상대 경로 + `.ts` 확장자**로 부르고 타입은 `import type`
으로만 가져온다. `node --test` 와 수동 실행 스크립트가 Next 없이 node 로 바로 돌리기 때문이다
(`@/` 별칭을 쓰거나 타입을 `import type` 없이 가져오면 거기서 깨지고, tsc 는 이걸 못 잡는다.
`imports.test.mjs` 가 잡는다). 이를 위해 tsconfig 에 `allowImportingTsExtensions` 를 켰다.

`pnpm test` 와 수동 실행은 **Node 22.18 이상**이 필요하다(.ts 를 그대로 실행하는 타입 지우기).
CI 는 22 라 문제없고, `.nvmrc` 는 20 이라 nvm 을 쓰면 이때만 22 로 바꾼다.

## 언제 무엇을 보내나

| 리포트 | 조건 | 중복 방지 |
| --- | --- | --- |
| 게시물 리포트 | 올린 지 3일 이상, 7일 미만이고 오늘 숫자를 받은 게시물 | 게시물마다 한 번. 7일 상한은 처음 켤 때 옛 게시물이 쏟아지지 않게 하는 장치. 오늘 숫자를 못 받았으면 다음 날로 미룬다 |
| 급상승 알림 | 가장 최근에 끝난 하루의 도달이 직전 14일 중앙값의 3배 이상이고 300명 이상 | 전날 날짜로 기록이 있으면 보내지 않고 기록만 남긴다 (같은 흐름은 며칠 이어져도 첫날 한 번). 직전 기록이 7일 미만이면 판단하지 않음 |

기준값은 `rules.ts` 맨 위 상수에 있다. 3일인 이유는 도달이 올린 날 튀고 사흘 안에 거의
멈추기 때문이다(2026년 9월 게시물 실측).

순위와 "보통 게시물"은 **그 게시물보다 먼저 올린** 게시물들의 최신 누적값과 비교한다. 나중에
올린 게시물은 아직 숫자가 작아서 섞으면 순위가 실제보다 좋게 나온다. 보통 게시물은 먼저 올린
게시물 도달의 중앙값이고, 비교 대상이 셋 미만이면 비교 문장을 뺀다.

급상승 알림의 "조회가 가장 많이 늘어난 게시물"은 그 하루가 시작되기 전 마지막 수집과 오늘
수집을 비교한다(`rules.ts` 의 `pickTopGain`). 급상승한 하루는 한국 시간으로 알림 이틀 전 오후에
시작해서, 바로 전날 수집과 비교하면 그 하루의 절반도 못 덮는다. 그 수집 뒤에 올린 게시물은
0회에서 시작한 것으로 센다 - 급상승을 만든 게 바로 그 새 게시물인 경우가 많다.

게시물 리포트는 오늘 숫자를 못 받으면 다음 날로 미루는데, 올린 지 6일이 넘은 날 실패하면
다음 날은 7일 창을 벗어나 그 리포트는 나가지 않는다. 드문 일이라 창을 늘리지 않았다.

계정 하루 지표를 못 받는 날도 게시물 리포트는 나간다(실행은 실패로 끝난다). 리포트는 3~7일
창 안에서만 나가서, 계정 쪽 문제로 며칠 막히면 그 게시물 리포트를 영영 놓친다.

## 인스타 API 에서 알아 둘 것

- 권한은 `instagram_business_basic`, `instagram_business_manage_insights` 둘뿐이다
  (Meta 앱 dongsim-metrics, 개발 모드). 댓글, DM, 게시 권한은 받지 않았다
- **릴스는 프로필 방문, 팔로우, 프로필 링크 클릭을 주지 않는다.** 물으면 요청 전체가
  거절돼서 종류별로 다른 지표를 묻는다. 대신 스킵률(처음 3초 안에 넘긴 비율)과 평균 시청
  시간을 받는다
- 프로필 링크 클릭은 `profile_activity` 를 `action_type` 으로 쪼갠 `bio_link_clicked` 다
- **하루는 미국 서부 자정 기준이다.** 하루 시계열의 `end_time` 은 이름과 달리 그 하루가
  시작하는 시각이다. 새 지표(views 등)는 하루씩 `total_value` 로 묻는데,
  `since=직전 하루의 시작+1초, until=시작` 이어야 시계열과 같은 값이 나온다. 1초라도 당기면
  이틀치가 합쳐진다. 자세한 실측은 `api.ts` 의 `fetchAccountDays` 주석
- 팔로워 수 추이, 팔로워 인구통계는 팔로워 100명부터 열린다 (2026-10 기준 79명)
- 게시물별 유입 경로(피드, 탐색 탭, 해시태그)는 API 로 열리지 않는다

## 토큰

60일이면 만료된다. 수집이 일주일마다 연장하고 연장한 값을 `metrics_tokens` 에 둔다
(환경변수는 수집기가 고쳐 쓸 수 없다).

- 처음에는 `INSTAGRAM_ACCESS_TOKEN` 환경변수를 받아들인다. 언제 만든 토큰인지 모르므로 만료를
  60일 뒤로 어림하고 바로 연장을 시도한다(만든 지 24시간이 안 됐으면 거절되고 다음 날 다시 한다).
  연장에 성공하면 인스타가 알려 준 진짜 만료로 바뀐다
- **토큰을 새로 발급했으면 환경변수만 바꾸면 된다.** 저장해 둔 해시와 달라지면 새 값을 받아들인다
- 연장이 계속 실패하고 만료가 10일 안으로 들어오면 실행이 실패로 끝난다(Actions 실패 메일).
  그때는 Meta 앱 > Instagram 로그인으로 API 설정 > 토큰 생성으로 새로 받아 환경변수를 바꾼다

## 환경변수

| 이름 | 어디에 | 값 |
| --- | --- | --- |
| `METRICS_CRON_SECRET` | Vercel, GitHub Actions 시크릿 | 같은 임의 문자열 |
| `INSTAGRAM_ACCESS_TOKEN` | Vercel | 인스타 토큰 (처음 한 번, 이후엔 DB 값을 쓴다) |
| `DISCORD_INSTAGRAM_WEBHOOK_URL` | Vercel | 리포트를 받을 채널의 웹후크 주소 |
| `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Vercel | 블로그와 같은 값 (이미 있음) |

## 처음 켜기

1. Supabase SQL 편집기에서 `supabase/migrations/0002_instagram_metrics.sql` 실행
2. 위 환경변수를 넣고 Vercel 재배포
3. 로컬에서 미리보기(아래 "손으로 돌리기")로 메시지를 확인한다. Actions 의 dry 실행도 되지만
   공개 로그에 메시지 본문(캡션, 숫자)이 찍히므로 로컬을 먼저 쓴다
4. 문제가 없으면 다음 날 오전 9시부터 저절로 돈다

## 손으로 돌리기

```bash
node --env-file=.env.local scripts/instagram-report.mjs          # 미리보기
node --env-file=.env.local scripts/instagram-report.mjs --send   # 실제로 보냄
```

미리보기도 숫자는 저장한다. 같은 날 다시 돌면 덮어쓰는 값이라 기록이 어지러워지지 않는다.

저장소가 공개라 Actions 로그는 누구나 본다. 크론 로그에는 요약(무엇을 보냈고 무엇이 실패했는지)만
남기고, 메시지 본문은 손으로 돌린 미리보기 때만 찍는다.

## 메시지 문구 규칙

[copy-guide.md](copy-guide.md)의 해요체를 따르고, 디스코드에서 읽히는 모양을 위해 이것을 더 지킨다.

- **첫 줄(굵게)에 무슨 일인지와 숫자 하나.** 휴대폰 알림에는 첫 줄만 보인다
- **한 줄에 숫자 하나, 단위를 붙인다** (회, 명, 개, 초). 디스코드 글꼴은 고정폭이 아니라 칸을 맞추면 틀어진다
- **헤더(`#`)와 이모지는 쓰지 않는다.** 헤더는 글자가 커서 짧은 리포트가 휴대폰 한 화면을 넘긴다.
  이모지는 봇 이름과 아이콘이 이미 하는 일을 반복한다
- 게시물 제목, 링크, 기준 설명은 **맨 아래 작은 글씨(`-#`)**. 링크는 `<주소>` 로 감싸 큰 미리보기 카드를 막는다
- 비교할 땐 기준을 같이 쓴다 ("보통 게시물(588명)의 3.9배예요"). 급상승은 첫 줄에 배수까지 넣는다
- 메뉴 이름을 문장에 그대로 쓰지 않는다. "계정 도달이 늘었다" 대신 "우리 인스타를 본 사람이 2,152명이에요".
  목록의 "도달"은 인스타 앱 인사이트와 같은 이름이라 그대로 둔다 (앱과 숫자를 맞춰 볼 때 바로 찾게)
- 멘션은 전송할 때 `allowed_mentions: { parse: [] }` 로 막는다. 캡션에 @everyone 이 있어도 울리지 않는다
- 문구를 바꾸면 `messages.test.mjs` 의 기대 문장도 같이 바꾼다. 테스트가 문구의 정본이다
